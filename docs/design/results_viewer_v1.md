# results_viewer_v1 — the dynamic results viewer ([B66], Frank's ask 2026-09-21)

STATUS: v1.0 DESIGN — written by the manager before any code (Frank:
"think about requirements and design first"). Implementation lane
builds to this note; deviations come back here first.

## 0. What it is

A single-page, client-side viewer over the canonical store's SET-GRAIN
results: pick engines, sets, regimes, forms and a metric; get a sortable
matrix that re-renders instantly. It is a READING AID, like the matrix
HTML pages — never a canonical surface, never a ranking input. The
canonical numbers live in `reports/` and `store/`; the viewer must show
numbers IDENTICAL to the reporter's (R11) or show nothing.

Frank's stated requirements, verbatim mapping: single page JS ✓ (R1),
selectable engines ✓ (R3a), selectable areas ✓ (R3b), sortable result
columns ✓ (R5), other selections like form ✓ (R3d), data cell
selectable ns/throughput ✓ (R4), regime broken out match/search
large/small ✓ (R3c), dynamic updates ✓ (R7), engine grouping
pcre2/pcrec ✓ (R3a), loads data files so it can be updated ✓ (R2),
works from file:// ✓ (R12).

## 1. The file:// constraint (R12) — decides the data format

`file://` pages cannot `fetch()`/XHR sibling files (null-origin CORS)
and cannot load ES modules; plain classic `<script src>` works
everywhere. Therefore:

- `viewer.html` — the whole app, self-contained (inline CSS+JS, no
  CDN, no build step; it must work on a plane).
- `data/manifest.js` — `BENCH.manifest({generated_utc, store_rows,
  files:[...], pins:{...}})`.
- `data/<subbench>@<version>.js` — one per set, each a single call
  `BENCH.load({set:..., rows:[...]})`. Regenerable independently.

The viewer registers `window.BENCH` before the data script tags; a
missing/stale data file degrades to a named per-set "no data" notice,
never a blank page. Updating = re-running the exporter; the HTML never
changes.

## 2. The exporter (R11) — number identity or nothing

`tools/viewer_export.py` (python3, stdlib + the pcrecbench package):
walks `store/index.tsv`, loads each set's newest record per
(testee_id, machine_id) — plus older-pin records when `--all-pins` —
and reduces to SET GRAIN **by calling the same `pcrecbench.reduce`
code path the reporter uses** (the [B10]/[B14] shared reduction), so a
viewer cell equals the committed report cell byte-for-value. It never
reimplements a median. Emits the `data/*.js` files atomically
(tmp+rename), with a `# generated by tools/viewer_export.py at <utc>
from index rows N` header inside the JSON payload's `meta`.

Per exported row (one per set × pattern × regime × form × testee):
`pattern, regime, form, testee_id, engine_family, engine_variant, pin
(or version), status (measured | refused | unsup | wrong | gave-up |
timed-out | inconclusive-*), median_ns, spread_lo_ns, spread_hi_ns,
subject_bytes_total (when the regime's reduction defines it — feeds
throughput), n_subjects, record_id, measured_utc`. Statuses other than
`measured` carry no numbers and are NEVER ranked (the standing
correctness-gates-the-scoreboard rule).

## 3. Filters and grouping (R3)

- **Engines (R3a)**: a two-level checkbox tree derived FROM THE DATA:
  family → variants (pcre2: interp/jit/dfa; pcrec: auto/nocaps/vm/
  vm-in; re2: default/longest; rust, oniguruma, tre, vectorscan: their
  variants). Family checkbox = tri-state toggle-all. Where `--all-pins`
  data exists, a per-family pin picker (default: newest per testee —
  the canonical-identity rule from reports/CLAUDE.md's [B61] entry).
- **Areas (R3b)**: sets as checkboxes (email-specimen, loglines,
  bounded, altwide, syntax, capability), versions shown.
- **Regime (R3c)**: broken out exactly as the records spell them
  (search_short / large-subject-throughput / match / compile …),
  derived from data, checkbox per regime — never hard-coded, so a new
  regime appears without a viewer change.
- **Form (R3d)**: plain / whole-subject / (n/a), derived from data.
- **Pattern search**: substring filter over pattern names.
- **Status filter**: show/hide non-measured rows (refusals etc. shown
  by default — they are findings, not noise).

## 4. The matrix (R4, R5, R6)

- Rows = (set, pattern, regime, form) after filters; columns = selected
  testees, grouped under family header bands (grouping visible, not
  just in the tree).
- **Metric radio (R4)**: `median ns` | `throughput MB/s` (=
  subject_bytes_total / median_ns × 1000; only where bytes are defined
  — elsewhere the cell says `n/a (no size)`) | `× best-in-row` (best =
  lowest measured, expectation-passing median among VISIBLE columns,
  recomputed on every filter change — the matrix convention, but live).
- **Sort (R5)**: click any column header — sorts by that testee's
  current-metric value (non-measured rows sink to the bottom in a
  stable order: wrong, refused, unsup, gave-up, timed-out); click
  again flips direction; also sortable by pattern name, set, best
  value. One sort key at a time, indicator in the header.
- **Status cells (R6)**: words in muted chips (`refused`, `unsup`,
  `wrong`, `gave-up`), never numbers, never ranked, excluded from best.
- Tooltips: spread (lo–hi), n_subjects, record_id, pin, measured_utc —
  the provenance travels with every number (the context-around-numbers
  rule).

## 5. Dynamic behavior (R7) and state

All client-side; re-render on every control change (≈850 rows × ≤16
columns — trivial, no virtualization needed; re-render budget <50 ms).
Selection state serializes into `location.hash` (shareable, and it
works under file://); `localStorage` remembers the last state as a
convenience only (try/catch, never required). Light+dark themes.

## 6. What it is NOT (scope fence)

No server, no build step, no external CDN (file:// on a plane), no
subject-grain drill-down in v1 (the subject-grain TSVs stay the deep
tool), no cross-machine comparison UI (one machine in the store today;
the field is carried, the UI waits), no editing, nothing written back.
The viewer never computes a number the reduction didn't already define.

## 7. Where it lives

`viewer/` at the repo root: `viewer.html`, `data/` (generated,
COMMITTED so a fresh clone works — regenerated at will), `CLAUDE.md`.
The exporter in `tools/` beside selfcheck.py. A `make viewer-data`
target runs the exporter. Gitignored nothing — the data files are
small (≈850 rows × ~200 B ≈ 400 KB total).

## 8. Acceptance (the lane's checklist)

1. `make viewer-data` regenerates `viewer/data/*.js` byte-stably on an
   unchanged store (deterministic ordering).
2. Five spot cells (one per metric × status class, chosen by the lane
   and named in its report) MATCH the committed matrix/report TSVs
   exactly.
3. `viewer.html` opened via `file://` (no server) renders, filters,
   sorts, and switches metrics with every data file present — and
   degrades by name with one data file deleted.
4. Non-measured cells never rank, never join best-in-row, and sink on
   sort, verified by a constructed filter state that isolates each
   status class.
5. Engine-family toggle, regime breakout, form filter, pattern search
   and hash round-trip each demonstrated (states listed in the lane
   report).

## 9. v1.1 amendments (Frank's review from results, 2026-09-21)

Frank's five notes, verbatim-mapped; [B67] implements:
1. BUG: deselecting an engine must REMOVE its column; no duplicate
   columns ever; deselecting a whole family (e.g. all pcrec) removes
   the whole band. Root-cause the tree→column propagation and the
   duplication (suspect: per-pin variants rendering as extra columns
   independent of the tree's selection keys).
2. The pin/git tag in headers is uninformative — show an ORDERED DATE
   instead (the column's newest measured_utc date, YYYY-MM-DD; the pin
   stays in the tooltip for provenance, never as the primary label).
   Ordering anywhere pins are listed = by date, not sha.
3. Per-engine DATA COVERAGE: show, in the engine tree (and/or the
   column header), what fraction of the CURRENT filtered rows that
   engine has measured data for (a % or n/N chip) — "is there data" at
   a glance.
4. Metric selection becomes CHECKBOXES (any subset), values STACKED
   within each cell in a fixed order (ns, MB/s, ×best), each line
   labeled tersely; single-metric selection keeps today's compact form.
5. SORTING works on the ×best metric (and any displayed metric): the
   column-header sort control targets one of the displayed metrics —
   default the first displayed; a small per-header affordance (or a
   global "sort by" tied to the metric checkboxes) picks which.
6. DEFAULT SELECTION = latest engines only: on first load (no saved
   state), select only each engine's NEWEST identity (newest-pin
   canonical variant per family; ablation/deny-flag arms and older
   pins deselected by default, still selectable). This also retires
   the 45-column default the v1.0 report flagged.
7. Engine selection lives in a DROPDOWN (a compact button opening the
   grouped tree as a panel) rather than an always-visible list.
