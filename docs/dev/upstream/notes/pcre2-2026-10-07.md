## Auto-possessification gives a different match than full backtracking for a top-level iterator reached through `(?R)`

**Pattern**: `(?:b(?R)a|a+)`

**Subjects**: `baa`, `bbaaa`, `baaa`.

**Reproduction** (plain `pcre2test`, no special build):

    printf '/(?:b(?R)a|a+)/\nbaa\nbbaaa\nbaaa\n' > default.pcre2test
    pcre2test -q default.pcre2test

    printf '/(?:b(?R)a|a+)/,no_auto_possess\nbaa\nbbaaa\nbaaa\n' > nap.pcre2test
    pcre2test -q nap.pcre2test

**Observed (default options)** vs **expected (`PCRE2_NO_AUTO_POSSESS`,
and Perl 5.40.1's answer to the identical unanchored pattern)**:

| subject | default | `PCRE2_NO_AUTO_POSSESS` / Perl |
|---|---|---|
| `baa`   | matches `"aa"` at offset 1-3   | matches `"baa"` at offset 0-3   |
| `bbaaa` | matches `"aaa"` at offset 2-5  | matches `"bbaaa"` at offset 0-5 |
| `baaa`  | matches `"aaa"` at offset 1-4  | matches `"baaa"` at offset 0-4  |

The two answers disagree on which substring matches, not merely on how
much backtracking was tried to get there.

**Why the default answer is wrong**: `baa` can only be matched end to
end (offset 0-3) by taking the first branch (`b` then a recursive call
of the whole pattern) and letting the recursive call's own `a+` give
back one `a` so the outer, literal trailing `a` has something to
match. Auto-possessification turns that `a+` into `a++`
(non-backtracking) because, read purely as static text, it sits at the
very end of the pattern with nothing following it — true for the
TOP-LEVEL occurrence of `a+`, but the possessified form also governs
the copy reached through `(?R)`'s recursive re-entry, which does have
something following it once the recursion returns (the outer branch's
trailing literal `a`). With that `a+` forced possessive, the recursive
call can no longer give the `a` back, the first branch fails
outright, and the engine instead reports the second branch's match
starting one byte later (`a+` alone, matching `"aa"`/`"aaa"`/`"aaa"`
at the shifted offsets above).

The `NO_AUTO_POSSESS` documentation describes the optimization as
something that only skips backtracking that "can never be successful" —
here it is not: the backtracking it skips is exactly how the correct
match is found. This also matches Perl's answer (`perl -E 'say $& if
"baa" =~ /(?:b(?R)a|a+)/'` prints `baa`, offset 0-3), and the
PCRE2 docs state recursive subroutine calls have been non-atomic and
re-enterable since 10.30, specifically so they can participate in
backtracking like this.

**A narrower form of exactly this bug was already fixed once**, for
recursion into a *numbered/named capturing group* (10.31, 2018, item
31 — Bugzilla #2232 — "Auto-possessification at the end of a capturing
group ... caused incorrect behaviour when the group was called
recursively ... Iterators at the ends of capturing groups are no
longer considered for auto-possessification if the pattern contains
any recursions"). That fix still works today — the isolation control
below confirms it:

    printf '/^(b(?1)a|a+)$/\nbaa\n' > ctrl_default.pcre2test
    printf '/^(b(?1)a|a+)$/,no_auto_possess\nbaa\n' > ctrl_nap.pcre2test
    pcre2test -q ctrl_default.pcre2test   # -> baa, offset 0-3
    pcre2test -q ctrl_nap.pcre2test       # -> baa, offset 0-3 (same)

`(?R)` recurses into the *whole pattern*, which has no enclosing
capturing-group bracket of its own, so the 2018 fix's guard (which
checks `cb->had_recurse` only when unwinding a capturing-group's
closing bracket, in `pcre2_auto_possess.c`'s handling of
`OP_KET`/`OP_KETRPOS`) is never reached for it. The code path actually
used for a top-level iterator — `OP_END`, reached when there is
nothing left in the compiled program to inspect — has no equivalent
`had_recurse` check at all; it unconditionally allows
possessification. We read this directly in `src/pcre2_auto_possess.c`
at both 10.46 and 10.49 (identical in this region, differing only in
unrelated formatting elsewhere in the file), and `git log` on that file
shows no change to this code path since.
