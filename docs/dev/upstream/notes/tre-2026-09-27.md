## Subject: `[\xHH-\xHH]` (and any `\`-escape) inside a bracket expression is read literally, not as an escape — TRE 0.9.0

Hi — I ran into behaviour in `tre_regncompb()`/`tre_regnexecb()` (the
byte-mode POSIX API, `REG_EXTENDED`) that looks like an unintentional
gap between two parts of the parser, and wanted to report it in case
it's useful.

**Pattern:** `[\x80-\xff]{2,4}`

**Expected:** matches 2 to 4 consecutive bytes in the range 0x80-0xFF
(every other regex library I checked — PCRE2, Oniguruma, RE2,
Hyperscan/vectorscan — parses this the same way; `\xHH` inside `[...]`
is a very common idiom across regex dialects).

**Actual:** the pattern compiles without error, but matches something
else entirely. A minimal reproduction (`repro.c`, attached/below)
shows:

    case A ("GET /products?category=shoes&sort=price"): tre=MATCH oracle=nomatch [0,3)
    case B (0x81 0x82): tre=nomatch oracle=match [0,2)

i.e. it matches plain ASCII text with no byte ≥ 0x80 at all, and
*fails* to match the actual high-byte pair the pattern is written to
catch.

**Cause, as far as I can tell from the source** (`lib/tre-parse.c`,
`tre_parse_bracket_items()`, TRE 0.9.0): this function reads bracket
contents directly off the raw pattern characters —

    if (re + 2 < ctx->re_end && *(re + 1) == CHAR_MINUS && *(re + 2) != CHAR_RBRACKET) {
        min = *re;
        max = *(re + 2);
        re += 3;
        ...
    }
    ...
    else {
        min = max = *re++;
    }

— with no escape processing of any kind: `\` is just an ordinary
character here. So the bracket content `\x80-\xff` is read as the
literal sequence `\ x 8 0 - \ x f f`, which turns into the range
`'0'`-`'\'` (0x30-0x5C: every ASCII digit, `:;<=>?@`, `A`-`Z`, `[`,
`\`) plus the two standalone characters `x` (0x78) and `f` (0x66,
already inside the range). That's exactly what explains case A above
(`G`, `E`, `T` are all in 0x30-0x5C) and case B (0x81/0x82 are outside
it).

What makes this look like a genuine gap rather than intentional
strictness: TRE *does* support `\xHH` as a hex-byte escape — but only
OUTSIDE a bracket expression (a separate code path, the top-level atom
parser's `case L'x':`, a good distance further down the same file). So
the same escape syntax is accepted in one context and silently
misread — never rejected, just silently misread — in the other. The
same mechanism affects any `\`-escape inside `[...]` (I also confirmed
it happening with `[\w:-]` and `[\s\x0b]` from two other patterns in
my own test corpus, not attached here since they're not needed to show
the mechanism).

I don't know whether the intended fix is to make bracket expressions
support the same `\xHH`/`\w`/`\s` escapes the top-level parser does, or
to have `tre_regcomp`/`tre_regncompb` return `REG_BADPAT` (or similar)
when a bracket expression contains a backslash it doesn't understand,
rather than silently treating it as a literal character. Either would
turn a silent wrong answer into either a correct one or a compile-time
error, both better than what happens today.

Reproduction attached (`repro.c`, `run.sh`) — self-contained, links
only `libtre` (`-ltre`), no other dependencies. Tested against both
the distribution package (Ubuntu, `libtre-dev 0.9.0-1build1`) and a
freshly built pristine copy of the `v0.9.0` release tag (currently the
latest tagged release) with identical results.

Thanks for maintaining TRE.
