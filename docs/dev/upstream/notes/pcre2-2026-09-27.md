All three still reproduce on PCRE2 10.48 (the current release,
2026-08-31, built from the official source tarball with
`./configure --enable-jit && make`) alongside the distro's 10.46
package; neither the 10.47 nor 10.48 ChangeLog mentions anything

attached as a file), the exact `pcre2test` invocation, and the numbers
we measured (single core, quiet 12-core x86_64 box, median where more
than one run is quoted).

A fourth candidate we investigated (a super-linear cost on
`(?R)`-recursion over text containing deliberately unbalanced
parentheses) is NOT included here: it reproduces identically on
PCRE2's plain interpreter, on its JIT (once given enough `jitstack` to
avoid its own — correctly reported — stack-limit error), and on a
wholly independent engine (Oniguruma), so we read it as inherent to
backtracking over that INPUT SHAPE (an unclosed `(` forces any
backtracker to scan to the subject's end before failing) rather than a
PCRE2-specific defect, and are not raising it.

## 1. JIT: severe cost cliff on a subroutine-calling pattern over a long non-matching run (U1)

**Pattern** (an RFC 5322 address-spec regex using PCRE2 subroutine
calls onto `{0}`-guarded definition groups):

    (?:(?<atom>[a-z0-9!#$%&'*+/=?^_`{|}~-]+)){0}(?:(?<qchar>[\x01-\x08\x0b\x0c\x0e-\x1f\x21\x23-\x5b\x5d-\x7f]|\\[\x01-\x09\x0b\x0c\x0e-\x7f])){0}(?:(?<label>[a-z0-9](?:[a-z0-9-]*[a-z0-9])?)){0}(?:(?<octet>25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)){0}(?:(?&atom)(?:\.(?&atom))*|"(?:(?&qchar))*")@(?:(?:(?&label)\.)+(?&label)|\[(?:(?:(?&octet))\.){3}(?:(?&octet)|[a-z0-9-]*[a-z0-9]:(?:[\x01-\x08\x0b\x0c\x0e-\x1f\x21-\x5a\x53-\x7f]|\\[\x01-\x09\x0b\x0c\x0e-\x7f])+)\])

**Subject**: N bytes of `a` (no `@` anywhere — cannot match). Generate
with, e.g., `python3 -c "print('a'*524288)" > subject.txt` (524,288 is
enough to see the effect clearly in well under a minute; the original
observation used 1,048,576 and a 60+ second timeout).

**Reproduction**: because the pattern contains `/` (inside a character
class), use a delimiter other than `/` in `pcre2test`, e.g. `,`. Build
an input file:

    printf ',%s,jit\n' "$(cat pattern.txt)" > input.txt
    cat subject.txt >> input.txt
    pcre2test -q -tm 1 input.txt      # or: time pcre2test -q input.txt

Compare against the SAME pattern and subject with `jit` removed from
the modifier list (the plain interpreter), and against the
hand-inlined version of the same grammar with NO subroutine calls
(substitute each `{0}`-guarded group's own body directly wherever
`(?&name)` calls it) — both finish in well under a millisecond at any
subject size we tried, including 1,048,576 bytes.

**Observed**: JIT-compiled matching is fast for N up to ~500,000
bytes, then crosses a sharp cliff: at N=501,000 it takes ~4.1 s; at
N=502,000, ~8.2 s; by N=524,288 it exceeds 45 s (still running); the
1,048,576-byte subject takes 75-90 s. The interpreter and the
no-subroutine-calls control both stay under 0.15 s at every size we
tested.

**Why we believe this is a JIT-vs-interpreter divergence, not merely
"a hard pattern"**: `pcre2test`'s `info` modifier reports `Last code
unit = '@'` for this pattern — PCRE2's own compile-time analysis
already knows the whole subject can be dismissed once no `@` is found,
independent of whether the pattern is later JIT-compiled. Adding
`no_start_optimize` to the INTERPRETER's own modifiers reproduces the
same catastrophic cost the JIT already shows (both then fail to
finish within a comparable budget) — this is what convinces us the
interpreter's speed here comes entirely from that check, and that the
JIT-compiled matcher does not get the same benefit once the pattern's
literal body is reached through subroutine calls (`(?&name)`).

**We checked whether this is a JIT-stack resource limit and it is
not**: at a fixed N=501,000 (`python3 -c "print('a'*501000)" >
subject_small.txt`), append the subject-line modifier `\=jitstack=N`
(kibibytes) and compare:

    printf ',%s,jit\n' "$(cat pattern.txt)" > input.txt
    { cat subject_small.txt; printf '\\=jitstack=1\n'; } >> input.txt
    time pcre2test -q input.txt        # jitstack = 1 KiB
    # ...then edit the trailing "\=jitstack=1" to "\=jitstack=65536" (64 MiB) and re-run

Both give the SAME clean "No match" (rc 0, no error of any kind) in
statistically the same ~4.1 seconds either way. (For contrast: a
DIFFERENT pattern we also tested — `\((?:[^()]|(?R))*\)` over text with
deliberately unbalanced parentheses — DOES exhaust the default 32 KiB
JIT stack and correctly reports `PCRE2_ERROR_JIT_STACKLIMIT`; that is
a distinct, working mechanism, and is not what is happening here.) We
were not able to pin down the exact closed-form cost growth past the
threshold (a `pcre2test find_limits` characterization was attempted
but is itself too slow to complete once the per-attempt cost is
already large) — what we can state confidently is that no documented
resource cap is involved on either side of the cliff.

## 2. JIT does not share the interpreter's whole-subject required-code-unit dismissal (U2)

**Pattern**: the same address-spec grammar as above, but hand-inlined
with NO subroutine calls — a milder, always-linear (rather than
cliff-shaped) version of the same underlying gap:

    (?:[a-z0-9!#$%&'*+/=?^_`{|}~-]+(?:\.[a-z0-9!#$%&'*+/=?^_`{|}~-]+)*|"(?:[\x01-\x08\x0b\x0c\x0e-\x1f\x21\x23-\x5b\x5d-\x7f]|\\[\x01-\x09\x0b\x0c\x0e-\x7f])*")@(?:(?:[a-z0-9](?:[a-z0-9-]*[a-z0-9])?\.)+[a-z0-9](?:[a-z0-9-]*[a-z0-9])?|\[(?:(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.){3}(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?|[a-z0-9-]*[a-z0-9]:(?:[\x01-\x08\x0b\x0c\x0e-\x1f\x21-\x5a\x53-\x7f]|\\[\x01-\x09\x0b\x0c\x0e-\x7f])+)\])

**Subject**: 1,048,576 bytes of `a` (again, no `@`):
`python3 -c "print('a'*1048576)" > subject.txt`.

**Reproduction**: as above (`,` delimiter, `-tm 50` for a stable
in-process median):

    printf ',%s,jit\n' "$(cat pattern.txt)" > input_jit.txt; cat subject.txt >> input_jit.txt
    printf ',%s,\n'    "$(cat pattern.txt)" > input_interp.txt; cat subject.txt >> input_interp.txt
    pcre2test -q -tm 50 input_jit.txt      # look for the "Match time" line
    pcre2test -q -tm 50 input_interp.txt

**Observed** (median of 50 in-process match calls each, single core):
the plain interpreter answers in ~18-24 microseconds; the JIT-compiled
matcher takes ~2.4-2.9 milliseconds — roughly 90-160× slower across
several repeated runs (against both 10.46 and 10.48). Both correctly
report no match, and both scale linearly with subject length — this is
a fixed per-byte-cost multiplier, not a cliff (contrast finding 1).
`Last code unit = '@'` is, as in finding 1, a property of the compiled
pattern independent of JIT; the interpreter's speed is consistent with
one `memchr`-class scan that never finds `@`; the JIT's cost (~2.5-3
ns/byte) is consistent with a real byte-by-byte scan attempt.

## 3. JIT is significantly slower than the interpreter on a pattern beginning with a quote character (U4)

**Pattern**: an HTTP access-log line match, compiled `First code unit
= '"'`:

    "(?:GET|POST|PUT|PATCH|DELETE|HEAD) [^ "]+ HTTP/1\.[01]" 5[0-9]{2}\b

**Subject**: 1,048,576 bytes of ordinary prose containing NO `"` byte
at all:

    python3 -c "u=b'the quick brown fox jumps over lazy dog '; n=1048576; open('subject.txt','wb').write((u*(n//len(u)+1))[:n])"

**Reproduction**: this pattern contains a literal `/` (in `HTTP/1`), so
avoid `/` as the delimiter — `~` works:

    printf '~%s~jit\n' "$(cat pattern.txt)" > input_jit.txt; cat subject.txt >> input_jit.txt
    printf '~%s~\n'    "$(cat pattern.txt)" > input_interp.txt; cat subject.txt >> input_interp.txt
    pcre2test -q -tm 20 input_jit.txt
    pcre2test -q -tm 20 input_interp.txt

**Observed** (median of 20 in-process calls each): the interpreter
answers in ~18-24 microseconds; the JIT-compiled matcher takes ~560-640
microseconds — roughly 23-34× slower, reproduced across three repeated
runs. As in finding 2, the compiled pattern's `First code unit` fact
is identical for both routes; only the runtime cost of using it
differs. (A milder ~1.8× version of the same ratio was also reported
at a much smaller subject-size grain in our own original observation —
a single ~100-300-byte log line — but we found that grain too close
to our own measurement noise floor to reproduce reliably as a
standalone case; the 1 MB figure above is the one we can stand behind.)
