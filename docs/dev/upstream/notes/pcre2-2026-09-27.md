## 1. JIT: severe cost cliff on a subroutine-calling pattern over a long non-matching run (U1)

**Pattern** (RFC 5322 address-spec, PCRE2 subroutine calls):

    (?:(?<atom>[a-z0-9!#$%&'*+/=?^_`{|}~-]+)){0}(?:(?<qchar>[\x01-\x08\x0b\x0c\x0e-\x1f\x21\x23-\x5b\x5d-\x7f]|\\[\x01-\x09\x0b\x0c\x0e-\x7f])){0}(?:(?<label>[a-z0-9](?:[a-z0-9-]*[a-z0-9])?)){0}(?:(?<octet>25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)){0}(?:(?&atom)(?:\.(?&atom))*|"(?:(?&qchar))*")@(?:(?:(?&label)\.)+(?&label)|\[(?:(?:(?&octet))\.){3}(?:(?&octet)|[a-z0-9-]*[a-z0-9]:(?:[\x01-\x08\x0b\x0c\x0e-\x1f\x21-\x5a\x53-\x7f]|\\[\x01-\x09\x0b\x0c\x0e-\x7f])+)\])

**Subject**: N bytes of `a` (no `@` anywhere — the pattern cannot match).

**Observed**: with the pattern JIT-compiled (`pcre2_jit_compile` +
`pcre2_match`), matching against this subject is fast for N up to
~500,000 bytes, then crosses a sharp cliff: at N=501,000 it takes ~4 s;
at N=502,000, ~8 s; by N=524,288 it exceeds 45 s (still running); the
originally observed subject, N=1,048,576, takes over 60 s. WITHOUT the
JIT (the plain interpreter, `pcre2_match` on a non-JIT-compiled
pattern), the identical call on the identical subject at every one of
these sizes finishes in under a millisecond.

**A minimal isolating control**: the SAME grammar, hand-written out
without any subroutine calls (`(?&atom)` etc. replaced by their literal
bodies inline), is instant under JIT at every size tested, including
N=1,048,576. So the cliff is specific to a JIT-compiled pattern that
reaches its matching body through subroutine calls, not to this
grammar or this subject shape in general.

**Why we think this is a JIT-vs-interpreter divergence, not merely "a
hard pattern"**: `pcre2test`'s pattern-info output reports
`Last code unit = '@'` for this pattern — i.e. PCRE2's own static
analysis already knows the whole subject can be dismissed the moment
it is established that no `@` occurs anywhere. Disabling that
optimization on the interpreter (`no_start_optimize`) makes the
interpreter just as catastrophic as the JIT already is; the JIT run,
by contrast, does not need `no_start_optimize` to be slow — it appears
not to have this benefit at all for a pattern reaching its match body
through subroutine calls.

A standalone reproduction (`pcre2test` input, `run.sh`, ~5-25 seconds
to run by default; a larger N reproduces the full 60+ second case) is
available on request.

## 2. JIT does not share the interpreter's whole-subject required-code-unit dismissal (U2)

**Pattern**: the same RFC 5322 address-spec grammar as above, but with
NO subroutine calls (fully inlined) — this is a milder, always-linear
version of finding 1's mechanism, isolated from the cliff above.

**Subject**: 1,048,576 bytes of `a` (again, no `@`).

**Observed** (median of 50 in-process match calls each, same process,
same compiled pattern): the plain interpreter answers in ~18-24
microseconds; the JIT-compiled matcher takes ~2.4-2.9 milliseconds —
roughly 100-160× slower, though both correctly report no match and
both scale linearly in the subject length (this is a fixed
per-byte-cost multiplier, not a cliff). `Last code unit = '@'` is, as
in finding 1, a property of the compiled pattern regardless of JIT —
the interpreter's speed is consistent with a single `memchr`-class
scan using that fact; the JIT's cost (~2.5-3 ns/byte) is consistent
with a real byte-by-byte scan attempt.

## 3. JIT is significantly slower than the interpreter on a pattern beginning with a quote character (U4)

**Pattern**: `"(?:GET|POST|PUT|PATCH|DELETE|HEAD) [^ "]+ HTTP/1\.[01]" 5[0-9]{2}\b`
(an HTTP access-log line match; compiled `First code unit = '"'`).

**Subject**: 1,048,576 bytes of ordinary prose containing no `"` byte
at all.

**Observed** (median of 20 in-process match calls each): the
interpreter answers in ~18-24 microseconds; the JIT-compiled matcher
takes ~560-640 microseconds — roughly 23-34× slower, reproduced across
three repeated runs. As in finding 2, the compiled pattern's own
`First code unit` fact is identical for both routes; only the runtime
cost of using it differs. (A milder version of the same ratio, ~1.8×,
was also observed at a much smaller subject-size grain — a single
~100-300-byte log line — but we found that grain too close to this
machine's own timing-loop noise floor to reproduce reliably as a
standalone case; the 1 MB figure above is the robust one.)

## 4. Interpreter: recursion (`(?R)`) cost on balanced-parenthesis matching is super-linear in subject size (U5)

**Pattern**: `\((?:[^()]|(?R))*\)` (balanced parenthesised expressions
via recursion).

**Subject**: mixed prose/structured text (mostly plain words, a sparse
minority of lines containing a balanced or — about 1 in 8 of THOSE —
deliberately unbalanced parenthesised expression), generated at two
sizes with a 16× size ratio (64 KiB and 1 MiB), same generator, same
per-byte statistical shape, different byte counts.

**Observed** (plain interpreter, no JIT; `pcre2test`'s `global`
find-all mode, summed per-match "Match time" divided by subject bytes):
the 64 KiB subject costs ~870 nanoseconds per byte; the 1 MiB subject
(a 16× larger buffer of the SAME statistical shape) costs ~8,800-8,830
ns per byte — roughly a 10× increase in per-byte cost for a 16× size
increase. The match COUNT itself scales close to linearly with size
(117 matches at 64 KiB, ~2,068 at 1 MiB, ~17.7×), so this looks like a
per-match cost that grows with the position/size of the match rather
than a fixed per-match constant. We have not read the interpreter's
recursion implementation to identify the exact mechanism; our working
guess is that each `(?R)`-style re-entry may re-walk or re-allocate
some amount of state proportional to the current match depth or
subject position, but that is a guess from behaviour, not a source
finding.
