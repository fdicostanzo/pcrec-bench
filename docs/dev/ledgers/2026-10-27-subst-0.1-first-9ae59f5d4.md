## 3. The three slow cases — the pcrec-auto mechanism stamps

| case | route | DFA prefilter | start | req_byte / req_run / why | VM start scan |
|---|---|---|---|---|---|
| 2 rare | VM (hybrid) | `memchr` | reverse-pass | 47 (`/`) / `admin/`@5 / emitted | none |
| 5b mask-email | DFA | `byte-class` | reverse-pass | 64 (`@`) / none / emitted | none |
| 7 url-tld-fix | VM | — | — | 47 (`/`) / `s://www.`@3 / emitted | first-class |

HYPOTHESES (from the stamps only; not measured):
- **2:** the candidate filter keys on `/` (byte 47), which occurs several times
  in every log line, so the hybrid wakes on almost every URL; a rarer landmark
  (the `admin/` run is already known) would cut candidates by orders of
  magnitude. libpcre2 JIT scans this case at 7.5 GB/s, pcrec at 2.8 GB/s.
- **5b:** the DFA prefilter is a `byte-class` over the leading class
  `[A-Za-z0-9._%+-]`, true on most bytes of the log; the required `@` is known
  (req 64) but is a whole-window pre-check, not the candidate driver. rust-regex
  (×3.16 faster) is consistent with driving candidates from the rare `@` and
  scanning back. pcrec-vm is ×3.1 slower than pcrec-auto here, so the DFA route
  is already the right one.
- **7:** VM only (backreference + lookahead), start scan `first-class`; the
  required run `s://www.` is emitted as a pre-check. libpcre2 JIT is ×3.9
  faster on the same backtracking semantics, so this is per-attempt VM cost
  or candidate count, not a route choice; auto ≈ vm (203 vs 206 ms).
