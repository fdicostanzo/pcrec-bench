**The `plain` vs `whole-subject` asymmetry is systematic and one-directional**:

where `plain` did not (`cls-upto-16384`, `cls-lazy-16384`, `nest2-64`,
`nest3-16`). No pattern goes the other way.

Same line for `auto-nocaps`. Both forms refuse (`compile-cost` table
`REPORT:1811+`: `cls-upto-65535` / `plain` and `/ whole-subject`, both
`did-not-compile=1`, `n costed 0`, no `artifact bytes`).

**`pcrec-vm` and `pcrec-vm-in` compile `cls-upto-65535` without complaint**
— both forms, 22,120 B, 152.3 ms / 153.1 ms total. So the refusal is
specific to the `auto` route: at abi 11 `auto` hits the NFA-state cap
**before** any [SEL-1] fallback can send the pattern to the VM, even though
the VM route builds the same pattern in 1.5-2.9 ms of emit-c. This is the
sharpest structural finding of the compile axis (candidate 3, §5).

**The refusal is not timed.** The `did-not-compile` compile row carries
`compile_outcome`, `cost_class`, `diagnostic`, `pattern_id`, `seq`, `trial`
— and **no `cost` object at all**. The wall time pcrec spends discovering
it cannot build the pattern is not in the record (ask (iv), §5).

forms: total 128.9-157.4 ms, emit-c **1.37-2.93 ms**, artifact 22,040-22,120 B
— including `cls-upto-65535`. The whole compile-time growth on this ladder
is `auto`'s DFA build.

**Two derived numbers the [ART-SIZE] size term asked for (I-15 (c)):**

1. **`.so` bytes per count** on the greedy class ladder, net of the 22,488 B
   floor artifact: 256 → 31.8 B/count; 4096 → 11.95 B/count; 16384 →
   11.98 B/count. Linear at ~**12 B of `.so` per count** above n=4096.
2. **`emit-c` is super-linear in the count**, net of the 1.76 ms floor:
   256 → 3.14 ms, 4096 → 425.9 ms, 16384 → 7,032 ms. Exponents
   log(135.6)/log(16) = **1.77** on 256→4096 and log(16.5)/log(4) = **2.02**

## 5. RANKED OPTIMIZATION CANDIDATES (pcrec D86 — one row at a time)

Ranked by the size of the measured gap, largest first, each with the
mechanism the stamps show.

**1. The end-anchored DFA that falls back to `dfa_match=search-filter`.**
`cls-upto-4096` / whole-subject, `match` regime: **405.9 ns vs 10.9 ns** on
`l-07` against pcrec's own VM — **×37 on one subject**, ×7.04 on the set.
`cls-atleast-4096` ×6.14 on the set. The same artifact class at
`cls-upto-256` (`unwrapped`) costs 10.4 ns on the same subject. Mechanism:
`engine=dfa`, `dfa_match=search-filter`, `dfa_prefilter=byte-class-bounded`,
`dfa_scan=unanchored`. [ENG-ABS] (abi 10) removed the reverse pass for
`unwrapped` artifacts; **it is not reaching the large-count class rungs or
the two large nests' plain artifacts**. Affected: `cls-upto-4096` (both
forms), `cls-upto-16384` (plain), `cls-atleast-4096` (both forms),
`nest2-64` (plain), `nest3-16` (plain). The gap is the biggest single-cell
ratio in the sample that is not a backtracking cliff.

**2. `auto` selects the counted DFA on exactly the rungs where the VM is
faster.** `cls-upto-16384` / throughput / `t-letters-004k`: DFA **3.61
ns/B** vs pcrec's own VM **0.61 ns/B** = **×5.96 slower**, and ×5.89 slower
than pcre2-jit. Same at 4096 and 256 (set ratios auto÷vm 2.05 / 2.05 /
1.98). The 32768 rung, which `auto` sends to the VM, is **5.5× faster than
the 16384 rung's DFA on the same subject**. In `search` the same inversion:
auto÷vm 2.81-2.82 at 256/4096/16384, 1.00 at 32768. Mechanism:
`engine=dfa`, `dfa_table=premultiplied`, `dfa_prefilter=none`,
~12 B of `.so` per count — a table too large for L1 on a run that stays
inside the class. **A selection knee on the count would win 2× on the set
and 6× on the worst subject, with no new code path** — the VM route already
exists and is already chosen one rung higher.

**3. The wasted DFA build under `auto`, at bounded's scale.** Up to
**2.415 s of emit-c** (`nest3-16` whole-subject) against **7.68 ms** for
the byte-identical `--engine=vm` artifact = **×315**; the worst ratio is
`cls-upto-32768` whole-subject at **×687** (1.778 s vs 2.59 ms). Seven cells
exceed ×300. This is O-8 §5(b)'s `level-context` number (×313 / ×211, 0.51 /
0.72 s) at **2.2× the absolute cost and 2.2× the ratio**. I-18 reports
[SEL-1.2] as "reported, not chartered" because the predictor needs a
corpus-wide correlation between exact NFA states and DFA overflow; bounded
now supplies **eight labelled points** on that correlation (the four ctx
rungs, `cls-upto-16384` whole, `cls-upto-32768` both forms,
`cls-lazy-16384` whole, `nest2-64` whole, `nest3-16` whole) against 40
non-overflowing ones. Note also that the ctx ladder's attempt cost is
**flat across the count** (389.6-397.6 ms plain for 64 / 256 / 1024 /
greedy-256), which is itself a data point about where the overflow happens.

**4. `auto` refuses `[a-z]{0,65535}` although its own VM builds it in
2.9 ms.** `pattern too large (NFA exceeds 131072 states)` under
`auto`/`nocaps`, both forms; `pcrec-vm` and `pcrec-vm-in` compile both
forms at 22,120 B / 152 ms and answer all three regimes at
**0.7-1.4× pcrec's own best**. The NFA-state cap is checked before any
[SEL-1] fallback exists, so a pattern the VM can trivially handle is
refused outright. This is a **routing** gap, not a capacity one; the fix is
the same rung [SEL-1] already built, moved earlier. (I-18's abi-12 rungs
are keyed on *DFA state cap* and *emit size cap*; neither is the NFA cap.)

miss** (273,214 ns / 102,400 B) against auto's memchr DFA at 0.016 ns/B —
**×169 on the floor row**, ×10,650 on `csv5` throughput, ×13.5 on `floor`
search. This matters because every [SEL-1] fallback lands on the VM, so a
pattern that overflows the DFA loses the prefilter as well as the engine.
I-18 (2) says abi 12 adds `_VM_PREFILTER_LANG` and rebuilds a prefilter on
the retry rungs — **this is the row that measures whether it works**, and
these are its BEFORE numbers.

**6. `nest2-4` in the `match` regime — pcrec-vm's own cliff.** `d-00017`:

ratio auto÷vm is 0.04. Mechanism: `vm_rungs CURSOR|FRAMES_BOUNDED`,
`vm_strats POSSESSIVE|BACKTRACKING`, `fast tier 8/5`. Small, listed for
completeness — the DFA already covers it under `auto`.

**Upstream (not pcrec, for `docs/dev/upstream_findings.md`):**
