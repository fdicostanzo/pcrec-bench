differently. §2/§3 do the compile axis; §4/§5 do the match axis; §6 is
the recommendation.

## 1. `alt-cyr-64`'s own shape, read off its own bytes

Extract §1. `alt-cyr-64` is 64 Cyrillic-word branches, `|`-joined:
**663 total pattern bytes**, branch lengths **4-14 B** (avg 9.375 B —
Cyrillic is ~2 B/char in UTF-8, so this is 2-7-character words), and
**only 2 distinct lead bytes** (`0xd0`, `0xd1` — the whole Cyrillic
block's UTF-8 lead-byte range).

## 2. The compile axis: alt-cyr-64 against altwide's own width ladder

`bench/altwide@0.2`'s NOTES.md table (extract §2) gives `w-64` as
**64 branches, 3-12 B each, 526 total bytes**; `w-96` as 96 branches,
804 bytes. `alt-cyr-64` MATCHES `w-64` on branch count exactly (64==64)
and sits **BETWEEN `w-64` and `w-96` on total pattern bytes** — 663 B is
(663-526)/(804-526) = **0.493**, almost exactly halfway. This is the
"place it on the curve" reading the set's own design note
(`utf8_set_v1.md` §5(d): "the BRIDGE rung … ONE rung, not a ladder") was
built for, and it works: alt-cyr-64 is not off the curve by any
structural measure available before a single number is compiled.

**Cross-pin/testee-family caveat, stated up front.** `alt-cyr-64`'s
pcrec records are pinned at **ce658cb7 (abi 33)**; altwide@0.2's most
recent pcrec sample is **25b1984f (abi 27)** — SIX abi steps behind
(abi 29 OPT-REQBYTE/-ENDWIN/-ANCHOR-VM, abi 30 OPT-FREQPICK/-REQPOS,
abi 31 OPT-PRECHECK-ADMIT's `req_why`, abi 32 the `[VAR]` module, abi 33
K64 fix A all land in between). Every ratio below is therefore a
**cross-pin** ratio; it is stated, not hidden. Separately, **altwide@0.2
has NEVER been measured against `pcre2-dfa`, `oniguruma`, `re2` or
`vectorscan-nosom` at all** (extract §3, "testee families with NO
altwide@0.2 counterpart"; confirmed against `store/index.tsv`'s own
testee list for `altwide@0.2`) — four of the utf8 side's eight
compiling testee families have no altwide comparator to check against,
period; this is a gap in altwide's own testee coverage, not something
this read can work around.

**Compile time, `alt-cyr-64` vs `w-64`/`w-96`, the 5 testee families
both sets share** (extract §3, `median_total_ns`, plain form):

| testee family | cyr/w-64 | cyr/w-96 |
|---|---|---|
| libpcre2-interp | 0.888 | 1.442 (w-96 itself non-monotone here — NOTES.md already flags the ladder as noisy at this rung) |
| libpcre2-jit | 1.030 | 0.698 |
| pcrec-auto-caps | 0.885 | 0.746 |
| pcrec-auto-nocaps | 0.888 | 0.747 |
| pcrec-vm-caps | 1.054 | 0.724 |
| pcrec-vm-in-caps | 1.071 | 0.735 |
| rust-default | 0.903 | 0.454 |

On **4 of 5 usable comparisons** (interp excluded as unreliable — see
above), `alt-cyr-64` compiles FASTER than or within 7% of `w-64` despite
carrying 26% more pattern bytes and sitting halfway to `w-96`. **No
testee family shows Cyrillic costing MORE to compile than an ASCII
alternation of the same branch count once byte-count is accounted for**
— if anything the trend is the opposite direction. Artifact size moves
the same way but smaller: pcrec's `auto` route is **+4.05%** bytes over
`w-64` (109,704 vs 105,432 B) and **-22.9%** under `w-96`
(142,296 B) — again landing close to `w-64`, not scaling with the extra
26% source bytes.

**Mechanism check, one compile row each, read directly (extract §5,
`pcrec-auto-caps`, no store index):** both `alt-cyr-64` (ce658cb7) and
`w-64` (25b1984f) select `engine=dfa`, `engine_sel=selected`,
`dfa_prefilter=byte-class`, `dfa_table=premultiplied` — **the SAME
mechanism family altwide's own P2 ("the DFA is predicted to absorb
width at constant match cost") already predicts and NOTES.md already
measures for the whole width ladder.** `alt-cyr-64` is not running on
some UTF-8-only code path; it is on altwide's own DFA/byte-class-prefilter
route. One real difference showed up and is flagged, not resolved:
`w-64` stamps `dfa_scan_edge=range` (`scan_edges=4`) where `alt-cyr-64`
stamps `none`/`0` — but `w-64`'s abi (27) predates `req_byte`/`req_run`/
`req_why` entirely (introduced abi 29/31), so this is at least partly an
abi-vintage difference, not necessarily a Cyrillic-vs-ASCII one; **not
separable from a two-record read**.

**Verdict, compile axis:** altwide's own width ladder — ALREADY
COMMITTED, no new pattern needed — brackets `alt-cyr-64`'s compile cost
closely on branch count and total bytes, on the DFA/byte-class-prefilter
mechanism `alt-cyr-64` itself selects, and shows NO extra cost
attributable to the encoding once branch/byte count is accounted for
(if anything, cheaper). **This settles R5's "family (d), not the
question" reading for the compile axis specifically**: the compile-time
cliff R5 measures is a within-utf8-corpus finding (`alt-cyr-64` against
74 mostly-single-construct patterns' OWN median, not against altwide),
and altwide shows the SAME branch count costs the SAME order of
magnitude to compile regardless of script. The six-abi-step / four-
missing-testee-family gaps above are the reason this is "closely
brackets", not "settles beyond doubt".

## 3. The match axis: what altwide's subjects can and cannot say

`alt-cyr-64`'s own `expectations.tsv` (extract §4) puts **2,996**
non-overlapping matches in `t-64k-cyr`'s 65,536 B — **1 hit per 21.9
bytes** — and **0** matches in `t-64k-asc`/`-lat`/`-cjk` (all `nomatch`).
`subject_facts.tsv` confirms `t-64k-cyr` is 88.3% multibyte, dominant
lead `0xd0`. `bench/utf8/pool_cyr.tsv` has 175 words; `alt-cyr-64`'s 64
branches are drawn from THIS SAME high-frequency pool used to GENERATE
`t-64k-cyr`'s running prose — the pattern is not an arbitrary sample, it
is (a subset of) the corpus's own vocabulary, which is the reason its
hit density is so high.

**`bench/altwide@0.2`'s own throughput subjects are a completely
different design** (extract §4, `manifest_throughput.tsv`): every
subject is **pure ASCII, zero bytes ≥ 0x80, anywhere in the corpus**,
and every hit count is **ENGINEERED**, not natural — `t-128k-clean`
(0 hits/131,072 B), `t-128k-sparse` (16/131,072 = 1/8,192 B),
`t-128k-dense` (1,024/131,072 = **1/128 B — altwide's OWN densest
throughput subject, still 5.8× SPARSER than `alt-cyr-64`'s natural
Cyrillic density**), `t-512k-sparse` (the size arm, same density as
sparse).

**Consequence, stated plainly: altwide CANNOT answer R4's ×420.3/×228.0
script-band question, structurally, not just because no member happens
to exist yet.** No altwide subject contains any non-ASCII byte at all,
so there is no altwide cell that could show "Cyrillic costs more per
byte than ASCII" even in principle — every altwide comparison is
ASCII-vs-ASCII by the set's own charter (§2.4: it stays byte-mode,
that's what `utf8_set_v1.md` deliberately does NOT duplicate). Separately,
even if an ASCII pattern of the right shape existed, altwide's densest
engineered hit rate is still 5.8× sparser than what `alt-cyr-64` sees
naturally on `t-64k-cyr` — so density, not just script, is unmatched too.

**The one no-hit-background comparison that DOES exist, and why it
points the OPPOSITE way** (extract §6): on their respective all-miss
backgrounds, `alt-cyr-64`/`t-64k-asc` reads **1.33 ns/B** (libpcre2-dfa/
-interp, cited from the R2-R7 addendum's own extract, not recomputed)
while `w-64`/`t-128k-clean` reads **2.38-623.85 ns/B** across rust /
pcrec-auto / pcrec-vm / libpcre2-jit / libpcre2-interp — **2-3 orders of
magnitude MORE EXPENSIVE per byte**, the opposite direction from R4's
ratio. The mechanism is candidate-start SELECTIVITY, not encoding: `alt-
cyr-64`'s first-byte filter is 2 values (`0xd0`/`0xd1`), IMPOSSIBLE in
ASCII text, so the miss-scan is near-`memchr`-cheap; `w-64`'s filter is a
26-letter bitmap, extremely common in English prose, so far more
candidate starts are opened and then fail deeper in. **This is squarely
inside altwide's OWN already-charted structure-arm axis** — `sh1-*`
(1 lead byte) / `nar4-*` (4) / `w-*`/`s-*` (26) already bracket "how many
first bytes filter this"; a 2-lead-byte ASCII pattern would land INSIDE
that family, not open new machinery.

## 4. Recommendation

**Compile axis: altwide already suffices.** No new pattern is needed —
§2 above IS the reading, built entirely from already-committed
`w-64`/`w-96` records plus one direct per-record mechanism check. The
addendum's own candidate item 1 ("the manager's call" whether alt-cyr-64
belongs to utf8 or altwide) can be answered for the compile axis alone:
**cite altwide's curve in `bench/utf8/NOTES.md` when R5 is next written
up**, per `utf8_set_v1.md` §2.4's own citation rule — nothing further to
build.

**Match axis: altwide does NOT suffice, and cannot be made to, without
leaving its own charter.** Two separate gaps, not one: (a) altwide has
no non-ASCII byte anywhere, so it structurally cannot test "Cyrillic
costs more than ASCII to match" even with a same-branch-count pattern;
(b) altwide's engineered hit densities top out at 1/128 B, 5.8× sparser
than `alt-cyr-64`'s NATURAL density on its own corpus — so even a
translated `alt-asc-64` run against altwide's existing subjects would be
measuring a different (much sparser) regime than what R4 actually
reports.

**If an ASCII control is built, it belongs in `bench/utf8@0.2`, not
altwide**, for the same reason §2.4 gives for keeping width itself out of
utf8: this is an ENCODING-axis question (utf8's own charter), and
altwide staying ASCII-only is deliberate (`utf8_set_v1.md`'s own
"no ladder" row). Its shape, if Frank charters it:

1. **`alt-asc-64`**: 64 ASCII-word branches with the SAME branch-length
   distribution as `alt-cyr-64` (4-14 B/branch, avg 9.375 B — i.e.
   English/ASCII words 4-14 characters long, not bytes, since ASCII is
   1 B/char) drawn from a comparably-common-word frequency pool (the
   existing `pool_asc.tsv`/`pool_lat.tsv` shape), so branch count AND
   total pattern bytes both match `alt-cyr-64` as closely as English
   vocabulary allows.
2. The pattern alone does NOT settle R4 — it needs a subject at
   `alt-cyr-64`'s OWN natural hit density (~1/22 B), which none of
   `utf8`'s or `altwide`'s current subjects provide at that density on
   an ASCII pool. The honest options are (i) a NEW ASCII throughput
   subject built by the SAME "draw from the same frequency pool used to
   generate this pattern's own words" method `alt-cyr-64`/`t-64k-cyr`
   already uses (natural density, not planted), so the comparison stays
   apples-to-apples in DESIGN METHOD as well as branch count and bytes;
   or (ii) accepting an engineered high-density ASCII subject and
   documenting that it changes the measurement's nature (planted vs
   natural) — a design choice for whoever charters it, not a call this
   read makes.
3. Either way it is 44+ subjects of design/generation work (new pool
   entries, a new throughput corpus, oracle re-derivation), not a
   drop-in addition to an existing set — worth stating plainly so it is
   not mistaken for "add one pattern.rxt line".

**Given (2)-(3)'s cost, and that §2 already settles the compile axis
without it**, this read's own recommendation is: charter the match-axis
control only if R4's finding is itself going to drive a pcrec ask (it is
currently a candidate, not an outbox item); otherwise the addendum's
existing "no ASCII 64-branch control in this set" caveat, now backed by
this read's density/lead-byte analysis, is enough to keep R4 read as a
census entry rather than a script-cost claim.
