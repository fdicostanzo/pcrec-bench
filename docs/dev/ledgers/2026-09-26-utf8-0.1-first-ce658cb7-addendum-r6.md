## 2. `cls-lead-pair` — the named witness (UD §6.3)

`[α-ω]+` (bytes `[\xce\xb1-\xcf\x89]+`), a class whose byte-level range
spans exactly TWO lead bytes (0xCE, 0xCF) — `memchr` takes one byte and
cannot filter it; UD §6.3's own claim is that the bitmap-skip arm
(`byte-class` in this project's `dfa_prefilter` vocabulary) must be
chosen instead. Extract lines 1-6, with `cls-high-range` (a many-lead-byte
class, U+0100-U+2000, three distinct lead bytes 0xC4-0xE2) as an
unplanned control read alongside it:

| testee | route | `dfa_prefilter` | `prefilter` (VM) |
|---|---|---|---|
| `auto` | dfa, selected | **`byte-class`** | — |
| `nocaps` | dfa, selected | **`byte-class`** | — |
| `vm` | vm, forced | — | `none` |
| `vm-in` | vm, forced | — | `none` |
| `auto` / `cls-high-range` | dfa, selected | `byte-class` | — |
| `vm` / `cls-high-range` | vm, forced | — | `none` |

**Verdict: CONFIRMED, on the route a filter is even attempted.** Both
DFA-route configs route the two-lead-byte class to `byte-class`, never
`memchr` — exactly UD §6.3's prediction, and NOT a class-cardinality
coincidence: the three-lead-byte control (`cls-high-range`) reads the
SAME mechanism, so the DFA route is not choosing `byte-class` only at
`cls-lead-pair`'s specific count. The two forced-VM configs read
`prefilter=none` on BOTH `cls-lead-pair` and its control — see §6 below;
this is the pinned testee's own definition, not a per-pattern decline.

## 3. Control-twin pairs that both compile on pcrec

The set's declared UCP twins (`cls-w-ucp`/`cls-d-ucp`/`cls-s-ucp`,
`ci-ucp-invariance`, `asr-b-cyr-ucp`) are `unsupported-by-declaration` on
every `pcrec-*-utf8` config (P5.a; pcrec has no UCP axis) and carry no
compile row to compare — not checkable here. Two families DO have both
members compiling, extract lines 15-66:

**(a) `qnt-lazy-2b` / `qnt-plus-2b`** (`utf8_set_v1.md` §5: "the lazy
twin — the control pair for `qnt-plus-2b`"). Both patterns are `é+?` /
`é+`. On every one of the four configs the two patterns stamp IDENTICAL
`engine`, `engine_sel`, `dfa_prefilter` (`memchr`), `req_byte` (195 =
0xC3, é's own lead byte) and `req_run` (`c3a9@0`). **No divergence of any
kind.**

**(b) `ci-ascii-control` against the six-member fold family it is "the
row every fold-set size above is read against"** (`ci-moskva`,
`ci-greek-run`, `ci-class-range`, `ci-neg-fold`, `ci-strasse`,
`ci-sigma`, `ci-turkish-i`). On both DFA-route configs all seven stamp
`engine=dfa`, `engine_sel=selected`; on both forced-VM configs all seven
stamp `engine=vm`, `engine_sel=forced`. **The engine ROUTE is uniform
across the whole family on both axes — no twin diverges from its
control.**

The one place the family does NOT read identically is `dfa_prefilter`
ITSELF: `ci-ascii-control`/`ci-class-range`/`ci-neg-fold`/`ci-strasse`/
`ci-sigma`/`ci-turkish-i` read `byte-class`; `ci-moskva`/`ci-greek-run`
read `memchr` (req_byte 208 = 0xD0, 206 = 0xCE). This is NOT an engine-
route divergence in R6's sense — it is the SAME mechanism correctly
tracking a byte-structure fact: `(?i)abc`'s ASCII fold turns the pattern's
own lead byte into a two-member set (0x41/0x61 etc — a bitmap is needed),
while Cyrillic/Greek's 2-byte UTF-8 lead byte (0xD0/0xD1, 0xCE/0xCF) is
SHARED by the whole case-fold pair — case-folding a Cyrillic or Greek
letter never changes its own lead byte, so the lead byte survives as one
fixed value and `memchr` still applies. `req_byte`/`req_run` stay stable
across `auto`/`nocaps` for every one of the seven.

**Verdict: NO control-twin engine-route divergence found in either
checked family.**

## 4. The offset-skip population beyond P1's pair (F-C6's declared narrowing)

Extract lines 68-93; P1's own pair reprinted for context (`req_why` on
every row here reads `emitted`, never `none`/`dominated`/`one-attempt`):

| pattern | bytes | `req_byte` | `req_run` | `dfa_prefilter` |
|---|---|---|---|---|
| `lit-offset-at-head` | `@é` | 64 (`@`) | `40c3a9@0` | `memchr` |
| `lit-offset-at-tail` | `é@` | 195 (é lead) | `c3a940@0` | `memchr` |
| `lit-run-3` | 日本語 | 230 (日 lead) | `e697a5e69cace8aa@0` | `memchr` |
| `lit-mixed-ascii` | `user@例え.jp` | 117 (`u`) | `7573657240e4be8b@0` | **`offset-set`** |
| `alt-shared-char` | 日本\|日曜\|日付 | 230 (日 lead) | `e697a5@0` | `memchr` |

Every value is IDENTICAL between `auto` and `nocaps`, and between `vm`
and `vm-in` on the fields the VM route carries (`req_byte`/`req_run`
persist on every artifact per abi 29+; `dfa_prefilter` is DFA-scope only,
so the VM rows read `-`). Each stamp is mechanism-legible:

- `lit-offset-at-head`/`-tail`: the WHOLE 2-3 byte literal is captured as
  one required run; the scanned byte (`req_byte`) is the run's OWN first
  byte — [OPT-FREQPICK]'s rule ("where a run ships, `RX_REQ_BYTE` reports
  the run's own scanned member," `testees/pcrec/CLAUDE.md`'s abi-30
  entry) applied consistently to both orderings.
- `lit-run-3`: the run is capped at `PCREC_MAX_REQ_RUN_EMIT` = 8 bytes
  (`e697a5e69cace8aa`, dropping 語's own trailing continuation byte
  `9e`) — the whole matchable literal minus one byte.
- `alt-shared-char`: the run is the 3-byte COMMON PREFIX only (`e697a5`
  = 日), correctly narrowed to what all three alternation branches
  actually share, not any one branch's full literal.
- `lit-mixed-ascii`: `dfa_prefilter=offset-set` (not `memchr`) — the
  [OPT-K] offset-set mechanism, the documented arm for a fixed-length
  prefix carrying more than one useful scan position (an ASCII run
  `user@` immediately followed by a high lead byte).

**Verdict: no engine-route divergence between `auto` and `nocaps` on any
of the five rows; every stamp is mechanism-appropriate for its own
pattern's byte structure, and none of the five reads a declined
prefilter despite each having an available lead byte.**

## 5. The forced-VM population's blanket `prefilter=none` — the config's own identity, not a decline

Extract lines 96-103, 2 + census run. **67 of 67** compiling patterns
read `prefilter=none` on BOTH `pcrec-vm-utf8` and `pcrec-vm-in-utf8` —
including the four lookbehind patterns (`asr-lb-fixed`, `asr-lb-varwidth`,
`asr-lb-neg`, `asr-lb-class`) that `auto`'s OWN analysis gives a REAL
hybrid prefilter on the identical pattern text (`prefilter=hybrid`,
`engine_sel=selected`, `vm_prefilter_lang=exact` — confirmed directly,
not inferred: `python3` query against the same records, engine_metadata
printed in full for the four rows). This reads as TOTAL, not partial,
and is the documented consequence of forcing the engine, not a per-
pattern engine decision: `testees/pcrec/CLAUDE.md` line 13 —

> `pcrec-vm` | `+ --engine=vm` | **the VM forced, prefilter off, so the
> VM derives the whole span independently**

`--engine=vm` is defined, in this project's own adapter documentation, to
skip the prefilter-build step ENTIRELY, not to attempt and decline it on
a per-pattern basis. `engine_sel=forced` on all 67 IS the engine route
the config forces, by construction; its "no prefilter" consequence
follows from the testee's own definition and is not a stamp fact that
varies by pattern. **This is filed here as context for §6's census, not
as an R6 finding** — a future reading of this rule should not mistake
the forced-VM population's uniform `none` for 67 separate "declined
prefilter" surprises.

## 6. Corpus-wide census: is there a declined prefilter anywhere with a strong lead-byte set?

Extract lines 95-172 (`auto`/`nocaps`; the VM census is §5's population).
Of 69 compiling (pattern, plain-form) pairs (76 patterns minus 5
`unicode-class-scope` unsupported minus 2 family-(f)/`prp-ingreek`
refusals — P5.a/P7.a's own populations, not re-derived here):

| `dfa_prefilter` / VM `prefilter` value | count (auto = nocaps) |
|---|---|
| `byte-class` | 34 |
| `memchr` | 20 |
| `offset-set` | 4 |
| `offset-set-bounded` | 2 |
| `memchr-bounded` | 1 |
| `hybrid` (VM, auto-selected — the 4 lookbehind patterns, §5) | 4 |
| **`none` (declined)** | **4** |

The four `none` rows: `asr-a-z` (`\A日本語\z`), `asr-b-midchar` (`\B`),
`cls-dot-rep` (`^.{5}$`), `lit-anchored-run` (`^日本語$`). Every one is
either FULLY ANCHORED to one position (`\A…\z`, `^…$`) or a zero-width
assertion that matches at (almost) every position (`\B`) — exactly the
documented "none's largest cause… the start state ACCEPTS" case
(`testees/pcrec/adapter.py`'s own `dfa_prefilter` field description). No
candidate-start filter is sound on a pattern anchored to a single search
position or accepting everywhere; none of the four has an available
"strong lead-byte set" that a filter is skipping.

**Verdict: no instance found, anywhere in the compiling corpus, of a
declined prefilter on a pattern carrying a strong lead-byte set the
filter could have used.**

## 7. Overall R6 verdict

**R6 SCORED, all four named sub-checks — NO ENGINE-SELECTION SURPRISE
FOUND on this sample:**

1. `cls-lead-pair` CONFIRMS UD §6.3 exactly (`byte-class`, never
   `memchr`) on the route a filter is attempted on (§2).
2. Both checkable control-twin families (`qnt-lazy-2b`/`qnt-plus-2b`; the
   `ci-*` fold family against `ci-ascii-control`) show IDENTICAL engine
   routes throughout; the one differing sub-mechanism (`memchr` vs
   `byte-class`) is fully explained by whether case-folding changes the
   pattern's own lead byte, not an engine-selection inconsistency (§3).
3. The offset-skip population beyond P1 (`lit-run-3`, `lit-mixed-ascii`,
   `alt-shared-char`) shows mechanism-appropriate `req_byte`/`req_run`/
   `dfa_prefilter` stamps with no route divergence between `auto` and
   `nocaps` (§4).
4. The corpus-wide "declined prefilter" population on the DFA route (4 of
   69 compiling patterns) is fully explained by anchoring or a
   zero-width, everywhere-matching assertion; none carries an unfiltered
   strong lead-byte set (§6). The forced-VM route's own blanket decline
   (67/67) is the pinned testee's documented definition, not a per-
   pattern surprise (§5).

This closes `[B97]`'s one OWED item: R6 is now fully scored — a clean,
checked "no finding," not an unscored gap.
