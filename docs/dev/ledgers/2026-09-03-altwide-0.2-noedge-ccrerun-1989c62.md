## 4. THE RAISED-CAP PAIR — WHAT THE CAP GATES, AND WHAT IT DOES NOT

### 4.1 The raise removes a gate and changes nothing else

Cell-by-cell across the 34 auto and 40 vm cells both arms compile (XD
table 2; REC from BIG against A2):

- **auto artifacts are BYTE-IDENTICAL** on all 34, on all three size
  quantities (`w-256 plain` 977,055 / 18,829 / 305,448 on both sides;
  `s-512 plain` 843,161 / 19,749 / 264,488; `ci-256 plain` 989,069 /
  19,048 / 305,816).
- **vm artifacts are EXACTLY +1 byte** on all 40, on both size
  quantities (341,111 → 341,112; 474,309 → 474,310; 456,882 → 456,883
  with code 450,860 → 450,861). **Derivation:** the VM emitter writes the
  code cap into the emitted source, and `500000` (6 characters) becomes
  `8388608` (7); the DFA emitter writes no cap, and the total cap's two
  spellings `1000000` and `8388608` are the same width, so auto moves 0.
  The +1 is fully accounted for and is not a compile difference.
- **`K=8/default` on all 106 VM legend lines across BOTH arms.** The
  raised cap selects the SAME size term as the default cap on every rung
  both compile, and on the twelve rungs only the raise can reach. `caps=`
  reads `500,000/1,000,000` on the plain arm and `8,388,608/8,388,608` on
  the raised one — that is the config speaking, not a decision. The DFA
  route prints no `K=` clause at all, so **this is a VM-route answer
  only**; the question of whether a raised cap moves a DFA-side size term
  is not one this stamp set can answer (ask (ii)).
- **timings: 89 of 90 comparable (pattern × regime) BIG ÷ plain ratios
  lie in 0.995–1.009**, across all three regimes. The single exception is
  `w-256` / search / vm at **1.087**, one cell, against a group whose
  worst other-core reading (18.42 %) sits on that same record.
- `sel=` is `selected` (66) / `forced` (66) and nothing else on the
  raised arms; no `size-cap-retry` fires anywhere.

**So the raised-cap testee is an AXIS, not a gate removed with side
effects** — which is what [B31]'s config half claimed and what a reader
of the twelve new rungs needs to be true.

## 5. loglines — THE SCAN EDGE, MEASURED AS A COUNTERFACTUAL

### 5.1 The arm is a clean one-variable control, and the legend proves it

`-fno-scan-edge` moves `edge=` to `none` and `edges=` to `0` on all

**Every pattern with a non-zero edge count is faster without the edge;

the O(1)-in-edge-count rewrite recovers the whole 8.2 % only if the term
it removes really is the per-edge one.

**3. The DFA source cap is reached at a width the VM code cap is also

**4. [LIM-2] — the projected-size bail, priced.** §3.3. A DFA-route

compiles.

**5. The `\b…\b` wrapper's DFA cost.** §3.2. `wb-256` refuses on the auto

**6. `pfx3-256` throughput is the last cell libpcre2's JIT wins.** §4.5.
×1.04, and only at 256 — pcrec's cost on this shape is flat in width

gone by 512. Lowest rank because it is the smallest margin in the file
