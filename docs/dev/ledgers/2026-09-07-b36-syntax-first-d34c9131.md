### §1.1 — R0-A: nine cells where TWO independent engines disagree with the oracle, and the harness cannot say "gave up"

The nine cells are the same on `pcre2-jit` and on all four pcrec testees:
the three balanced-paren recursion spellings × the three throughput runs.

```
rec-r-uc  \((?:[^()]|(?R))*\)        t-64k / t-256k / t-1m
rec-1     (\((?:[^()]|(?1))*\))      t-64k / t-256k / t-1m
rec-name  (?<p>\((?:[^()]|(?&p))*\)) t-64k / t-256k / t-1m
```

The recorded diagnostic is identical on jit and on pcrec-auto for
`rec-r-uc` / `t-64k`:

```
"expected 116 non-overlapping match(es); observed 5"
observed: {"matched": true, "span": [464, 473]}
```

The FIRST match span agrees on all three engines. Only the COUNT differs.

**A read-only ctypes probe settles it.** Running the drivers' own advance
rule (`pos = max(match_end, pos+1)`) over `bench/syntax/throughput/t-64k.bin`
with libpcre2 10.46, interpreted and JIT-compiled, and reporting the raw
`pcre2_match` return code at the step where the loop stops:

```
interp: count=116  stop_rc=-1   (no match)
        first_spans=[(464,473),(477,480),(1994,2009),(2013,2025),
                     (2027,2045),(2119,2128),(4149,4161),(4165,4192)]
jit:    count=5    stop_rc=-46  (JIT stack limit reached)
        first_spans=[(464,473),(477,480),(1994,2009),(2013,2025),(2027,2045)]
```

The first five spans are IDENTICAL. The JIT then returns
**`PCRE2_ERROR_JIT_STACKLIMIT` (−46)** and the loop stops.

**So this is not a semantic divergence. It is a give-up that the harness
renders as a wrong answer** — and requirements §4.4 says a give-up is a
first-class result, not a wrong answer. The cause is in BOTH drivers, in
the same three lines:

- `testees/pcre2/driver.c:321-340` — `if (rc < 0) { if (count == 0) rc_final = rc; break; }`
- `testees/pcrec/driver.c:714-731` — `if (r < 0) { if (count == 0) giveup = r; break; }`

A negative return **after** the first match is discarded, the loop breaks,
and the shorter count is reported as the answer. `pcrecbench/oracle_pcre2.py`'s
`_find_all_impl` has the same shape (`if got is None: break`), which is
harmless there because the oracle is the interpreter and the interpreter
does not give up on this corpus — but it means the oracle cannot ever
witness the condition either.

pcrec's four testees stop at the same 5 with the same first span. The
probe cannot be run against a pcrec artifact without a build (out of this
lane's scope), so the pcrec half is a STRONG HYPOTHESIS, not a
measurement: pcrec's `do_search` returns a negative give-up code mid-loop
on the same subject and `giveup` is discarded for the same reason. The
falsifying test is the same one-line fix, and it tests both at once.

**Scored against NOTES:** these nine cells are the census's own
"Give-ups and refusals are results" section (`bench/syntax/NOTES.md`)
failing on its own terms — "Nothing here should give up at match time"
is REFUTED, and refuted invisibly, because the instrument cannot spell
the outcome.

**Collateral:** because the set-grain reduction excludes a set cell if any
subject fails, `rec-r-uc` / `rec-1` / `rec-name` × `large-subject-throughput`
rank with ONE testee in the whole table (report line 5229: the interp
alone, and flagged `**dominated**: t-1m is 93.9 % of this set`). Five of
the six testees are silently absent from three of the set's 285 rankings.

`testees/pcrec/driver.c:714-731` both read
`if (rc < 0) { if (count == 0) <giveup> = rc; break; }` — a negative
return after the first match is discarded.
**Falsifiable by:** distinguish `PCRE2_ERROR_NOMATCH` (and pcrec's `0`)
from every other negative code in both loops; report the code as a
`gave-up` outcome per requirements §4.4; re-run the nine cells. If the
counts still read 5, the finding is a semantic divergence after all and
this question becomes an upstream one. `pcrecbench/oracle_pcre2.py`'s
`_find_all_impl` needs the same treatment or it can never witness the
condition.
**Why first:** it silently removes five of six testees from three of the
census's 285 rankings, and it can do so on any set with a deep
backtracking construct.

**Q2. Why can the whole-subject form not report a match start other than
0?**
Cell: `asr-k-uc` (`key=\K\w+`) / `match-compliance` / `whole-subject` /
`f-kv` on all four pcrec testees. Recorded:
`expected span [4,9]; observed [0,9]`; libpcre2 answers `[4,9]`.
Source: `testees/pcrec/driver.c`'s `anchored` branch sets

**Falsifiable by:** having the whole-subject path report the artifact's
own reported start rather than a constant, then re-running that one cell.
If pcrec's `do_match_caps` cannot report a start, the question moves to
pcrec as an ABI ask.
**Why here:** P9 exists precisely to catch this, it caught it, and the
answer is in our own source — but the same defect silently converts every
`\K` (and any future match-start-reset construct) into a wrong answer on
one whole testee family.

**Q3. Should the `(?:<pattern>)\z` whole-subject wrapper be built
lexically at all?**
Three cells, three different failure modes, one cause:
`rec-r-uc` / `f-parens` (P2's predicted wrong answer, `(?R)` recursing
into the wrapper); `mod-x` (`(?x) c a t # comment`) refusing to compile
at all with `pcrec: missing closing ) for group (pattern offset 0)`
because the `/x` comment swallows `)\z`; and Q2's `\K`.
Control: libpcre2 reaches the same regime through
`PCRE2_ANCHORED|PCRE2_ENDANCHORED` on its ordinary artifact and hits none
of the three.
**Falsifiable by:** a single-character probe set — append `\n` to a
wrapped `/x` pattern and see `mod-x` compile; that isolates the comment
half from the recursion half. The general fix is an anchoring FLAG in
pcrec's own interface rather than a textual wrapper (pcrec [OS-4], which
the reporter already cites in its own legend at every match-compliance
table).
**Why here:** it is one mechanism producing an R0, an R1 and an R0 across
three unrelated syntax families, and every future set inherits it.

### Tier B — general engine mechanisms

**Q4. Why does the forced-VM route not treat `\G` as an anchor when it
treats `^` and `\A` as one?**
Cell: `anc-g-uc` (`\Gitem`) / `large-subject-throughput` on
`pcrec_d34c9131_vm-caps-simdna` — **1,219,696.7 ns/set** against
`anc-caret`'s **15.1** on the same testee (×80,784) and against the JIT's
106.5 (×11,457). Report line 331.
Control: `anc-caret` and `anc-a-uc`, same spelling group, verified
identical answers on all 8,265 rows; and the `auto` route, where all
three compile to `engine=dfa dfa_scan=attempt dfa_prefilter=none
dfa_match=search-filter` and cost 16.9 / 16.9 / 18.7 ns.
Stamps: the three forced-VM artifacts are IDENTICAL on every stamp —
`engine=vm engine_sel=forced islands=0 clsfolds=0 frameless=1
shape=forward` — differing only in `vm_program_bytes` (801 / 801 / 814).
Per-byte 0.8914 / 0.8866 / 0.8858 at 64 KB / 256 KB / 1 MB: a flat
full-subject scan.
**Ask that travels with it:** no stamp in the record distinguishes an
anchored VM program from an unanchored one. A ×80,784 route difference is
invisible to the reporter. An `RX_VM_ANCHORED` (or a `shape` token) would
make it a bucket instead of a discovery.

**Q5. Why does a CAPTURE requirement move the route, and is the price
right in every regime?**
Cells: `grp-cap` (`(cat)`), `grp-named`, `grp-named-quote` and the four
four-digit calls — seven patterns, both forms, where
`pcrec_d34c9131_auto-caps-simdna` compiles `engine=vm engine_sel=selected
lang=exact` and `pcrec_d34c9131_auto-nocaps-simdna` compiles
`engine=dfa`. The `-nocaps` arm is a one-variable control already in the
roster.
Measured price, `auto ÷ nocaps`: **match 0.519–0.628** (the capture route
is ×1.6–×1.9 FASTER), **search 1.181–1.228**, **throughput 1.099–1.158**
(slower). 23 of 285 set cells differ by >5 % between the arms; all 23 are
these seven patterns.
**The question:** the hybrid already carries a DFA prefilter
(`dfa_prefilter=memchr`, `vm_prefilter_lang=exact` on `grp-cap`) and still
pays ×1.10–1.23 on the scanning regimes against the pure DFA. Is the
residual the VM's per-candidate entry, or the capture bookkeeping itself?
The `match` column says the machinery is not intrinsically slow.
**Falsifiable by:** a depth probe of the bounded-rung shape crossing
capture count (0, 1, 2, 4) with body held fixed, at three hit densities.

**Q6. Why is `shape=inline` ×1.78 FASTER than `shape=forward` on one pair
and ×2.9–5.1 SLOWER on another?**
Fast direction — forced VM, the `cat` spelling group, verified identical
answers (§4.4):
`grp-cap` `(cat)` `shape=inline prog=800 B` **961,162.7** vs `lit-cat`
`cat` `shape=forward prog=551 B` **1,714,697.1** (×0.561 tput, ×0.575
search); `grp-named` and `grp-named-quote` reproduce it to 0.2 %.
Slow direction — `auto` route hybrids:
`lkb-pos` `(?<=item )done` `shape=inline frameless=1` **4,033,554.7** vs
`lkb-neg` `(?<!item )done` `shape=plain frameless=0` **791,530.2**
(×5.09); `lka-pos` vs `lka-neg` ×2.91. The two artifacts of each pair
agree on `dfa_prefilter=offset-set`, `offsets=0,2*` (resp. `0,3*`),
`vm_prefilter_lang=exact`, `resume_frames=3` (resp. 2) — `shape` and
`frameless` are the only stamps that differ.
**The confound, stated:** the pos/neg pairs denote different languages and
match at different densities. Two facts argue the shape is implicated
anyway: the same pairs are ×1.03 and ×1.12 in the SHORT regime where the
m/n facts are known (2/42 vs 6–7/42 hits), so the gap opens only per byte;
and the direction is backwards for a hit-count story, since the negative
forms have ~3× the hits and are 3–5× faster.
**Falsifiable by:** an entry-shape DENY FLAG on pcrec's side (the shape of
`-fno-alt-island` / `-fno-cls-fold`), which would turn both pairs into
one-variable pairs at one pin. That is the ask. `lkb-pos` at
**auto ÷ jit = ×20.06** is the worst `auto` cell in the whole census and
it is the one this flag would explain.

**Q7. Should a possessive quantifier or an atomic alternation force the
VM on a pattern whose language is finite?**
Cells, `auto` route, all with `captures 0, backref_max 0,
max_lookbehind 0` in `pattern_facts.tsv` (R6's REGULAR test):
- `grp-atomic-alt` `(?>a|ab)c` → `engine=vm shape=plain frameless=0
  prog=1,321 B`; its atomic twin `grp-atomic-rep` `(?>a+)b` →
  `engine=dfa memchr edge=range`. Throughput 993,025.9 vs 812,182.6
  (×1.22), and ×2.46 the JIT. The language is `{ac}`.
- `qnt-poss-quest` `a?+a` → `engine=vm shape=forward prog=784 B`;
  `qnt-poss-star` `a*+b` and `qnt-poss-brace` `a{1,2}+b` → `engine=dfa`.
  Throughput **2,005,118.9** vs `qnt-star` `ca*t` (dfa) 858,659.6 —
  **×2.34** — and ×1.66 the JIT. The language is `{a, aa}`.
- `qnt-poss-plus` `a++ab` → `engine=vm shape=forward`; its control
  `qnt-plus-ctl` `a+ab` → `engine=dfa offset-set`. SEARCH 1,511.2 vs
  750.9 = **×2.01** (P4's refutation, §6).
**The question:** three of the four possessive suffixes take the DFA and
two take the VM; the split is not the suffix. What predicate is it, and
does the finite-language case belong on the automaton side?

**Q8. Why is `dfa_prefilter=offset-set-bounded` a ×2.4 tier?**
Six cells, `auto` route, throughput, against `pcre2-jit` (§3.1):
`done$` ×2.419, `done\Z` ×2.424, `done\z` ×2.458, `(?m)done$` ×2.393,
`\bcat\b` ×2.512, `\Bcat\B` ×2.719. The band is **2.393–2.719** — tighter
than any other prefilter bucket in the set.
Control: the same testee's other 49 DFA cells, whose medians by prefilter
are `none` **0.158**, `memchr` **0.728**, `byte-class` **0.997**,
`offset-set` **1.286** — a monotone ordering over six buckets.
Adjacent evidence: `(?i)cat` drops from `memchr` to `byte-class` and pays
×1.62 against its own non-caseless twin while the VM's masked compare pays
×1.26 (§7.3); `cat|dog` and `(?:c|d)(?:at|og)` are `byte-class` at
auto ÷ jit 1.70 / 1.77.
**The question:** is the bounded variant's cost the bound check per
candidate, or a prefilter that should not have been chosen? The
`done$`/`\Z`/`\z` trio has `first_code_unit 'd'` and a required unit —
PCRE2 gives them a first-code-unit scan and wins ×2.4.
**Why below Q4–Q7:** the likely fix is a better prefilter *choice* (a
mechanism), but the residual after choosing right is a scan-tier constant
(Q10).

### Tier C — upstream (libpcre2), for `docs/dev/upstream_findings.md`

**Q9. libpcre2 10.46's interpreter is quadratic in subject length on

### Tier D — the scan tier, where "SIMD would help" is the honest answer

**Q10. The single-literal scan is ×1.5 behind the JIT on the DFA route
and ×35 behind on the forced-VM route.**
`auto ÷ jit` on the literal-scan cells: `lit-cat` **1.534**,
`cls-n-uc` (`it\Nm`) 1.608, `cls-s-lc` (`cat\s+sat`) 2.529. `auto`'s
artifact is `dfa/memchr`; the JIT's advantage on a first-byte scan is a
constant factor, not a mechanism.
The forced-VM half is larger and is a mechanism after all: `floor` (`#`,
a full-length miss over 1.3 MB) is **0.622 ns/B** on `vm` against
**0.0177** on `auto` and 0.0397 on the JIT — ×35.2 and ×15.7 — on a
`shape=forward prog=236 B frameless=1` artifact that carries **no
prefilter stamp of any kind** (§8). Every single-literal forced-VM cell
sits on it (`esc-tab` ×15.5, `esc-quote` ×13.4, `esc-cr` ×10.1 vs the
JIT). Read beside [B35] (9') and outbox O-21, which argue the same
instrument at fixed-cost scale; at 1 MB it is per-byte.

**Q11. The dense-class cells are the most expensive in the set and pcrec
already leads them.**
`\w+`, `[[:alpha:]]+`, `(?a)\w+`, `\S+@\S+` — ~200 k matches per MB, so
per-MATCH cells, not scan cells (P7 confirmed). `auto ÷ jit` = **0.537 /
0.560 / 0.532 / 0.958**; the forced VM is faster still on three of the
four (`\w+` 5,720,072 vs `auto` 6,883,405). `\p{L}+`, `\P{L}+` and
`(?[[a-z]-[aeiou]])+` are pcrec refusals (§2.1), so the property and
extended-class arms of this question are unmeasurable at this pin.
**Listed last deliberately:** it is the largest absolute cost in the
census and the place pcrec is already ahead. It is here so the next reader
does not mistake the big numbers for the open questions.

**Q12. `auto`'s per-byte cost rises with subject size on sparse-hit
patterns; the JIT's does not.**
Nine R7 cells at `t-1m ÷ t-64k` = **1.42–1.74**, seven of them on
`auto`/`nocaps`: `esc-octal-0` 1.42/1.45, `esc-tab` 1.49/1.50,
`esc-quote` 1.59/1.60, `grp-noncap` 1.65/1.67, `cls-h` 1.73/1.73
(plus `jit cls-negset` 1.61 and `vm-in rec-define` 1.72). A working-set
or prefetch effect the census can only flag; the depth probe is a size
sweep with more rungs on one of those five patterns.
