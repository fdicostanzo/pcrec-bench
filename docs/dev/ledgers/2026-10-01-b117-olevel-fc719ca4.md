**The split is 100% clean across the whole 62-pattern population, not just
these 14**: every one of the 22 `pcrec-vm` patterns whose `req_byte` DOES
occur in the throughput subjects (counts 2,289-44,132 across the three

slowdown (ratios 2.41-7.87); the 14 zero-occurrence patterns are the ONLY

does not carry this one — it is a scratch, reproducible-from-committed-data
derivation, not archived as a probe; the method is stated here in full so
anyone can re-run it.)

**Mechanism, stated as a measured reading, not a guess**: pcrec's own
necessary-byte pre-check ([OPT-REQBYTE]/[OPT-REQPOS], `RX_REQ_BYTE`/
`RX_REQ_WHY "emitted"` on all 14) performs ONE linear scan for the
pattern's scanned byte (functionally a `memchr`-shaped guard) before the
VM's goto-threaded dispatch loop is ever entered. When that byte is ABSENT
from the subject — true for all 14, confirmed by direct byte-count — the
scan runs once over the whole buffer and returns "no candidate," so the
subject is dismissed WITHOUT the VM dispatch loop executing even once.
Absolute magnitudes confirm it: `floor-byte` (this set's own designated
near-zero-cost floor pattern — `floor_pattern: floor-byte` in the report
header) and `mojibake-curly-quote` (also zero-occurrence) both read ~23.1
microseconds summed over all three throughput subjects (1,372,160 bytes)
at EVERY `-O` level — essentially flat because essentially nothing but a
single linear scan ever runs, and that scan's own compiled machine code
belongs to the necessary-byte guard's host library, not to code our
phase-2 `-O` flag recompiles (pcrec's own emitted guard is a thin,
already-tiny branch in front of the scan; the scan itself is the
dominant cost and is NOT pcrec's own emitted C). By contrast
`wild-codegrammar-json-array-begin` (`req_byte` `[`, 382-5,985 occurrences
per subject — the VM dispatch loop genuinely runs many times) reads
1.11 ms at `-O2` and 10.18 ms at `-O0` — ×9.20, this window's single
largest mover, on the SAME testee, same regime, same subjects.

**The `.so` artifact DOES differ in size for all 14 "flat" patterns at
`-O0`** (+240 B to +8,512 B, per the table above — the same no-dead-code-
elimination cost §3/P7 already names) — the compiled code genuinely
changes, but that differing code is IRRELEVANT to these 14 cells' measured
runtime, because the differing (VM dispatch) code path is never reached on
these particular (pattern, subject) pairs. This is NOT-DETERMINED for
anything beyond these 14 named patterns and the two throughput subjects
checked — a different regime's subjects (`short-subject-search`'s ~75 smaller texts)
were NOT re-checked for the same byte-occurrence property, and
`short-subject-search`'s own `-O0` ratios for these SAME 14 patterns are
NOT flat — directly computed, they read 1.76×-2.31× (`wild-validator-
email-owasp` lowest, `tag-depth3-bound`/`nested-comment-rec` highest),
clearly slower though less extreme than the whole `pcrec-vm`/search/`-O0`
population's own range (§2: 1.68×-6.36× unsplit, all 62 patterns). This is CONSISTENT with the
short-subject population containing at least one text, per pattern, where
the necessary byte DOES occur (search regime subjects are designed to be
varied, unlike the three shared throughput texts) — but this was not
individually verified byte-by-byte here, so it is stated as a consistent
reading, not a confirmed one.
