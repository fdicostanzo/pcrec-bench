# R5 — `docs/design/capability_set_v1.md` v0.1, critic lens: engine semantics and measurement validity

**Reviewer:** lane `r5critic-semantics`, read-only, 2026-09-12. **Target:**
`docs/design/capability_set_v1.md` v0.1 "draft for panel", merged 08b1815.
**Charter:** refute, not admire. Every finding cites the target by section
(and, where useful, line) and the evidence by file:line or fetched claim
already in a committed research note. This lane touched no other file and
built/ran nothing (`bench/`, `schema/`, `pcrecbench/`, `testees/` untouched,
per the D6 mandate).

**Scope of this lens.** Engine semantics (is a REQUIRES/capability claim
actually true and correctly grounded) and measurement validity (does the
instrument — the calibration model, the schema, the driver protocol —
actually measure what the design says it measures). I did not re-review
provenance/licensing (§4), the `.rxt` decision (§9), or the build plan
(§11) except where they intersect this lens.

## Verdict

Four BLOCKING findings (S1, S3, S4, S6), three SHOULD-FIX (S2, S5, S7, S8 — four, see below), four WORTH-NOTING (S9, S10, S11). Correcting the count: **BLOCKING: S1, S3, S4, S6 (4); SHOULD-FIX: S2, S5, S7, S8 (4); WORTH-NOTING: S9, S10, S11 (3).**

The note's engine-semantics claims are, with two real exceptions (S1, S3), well-cited and hold up against both N2 and a fresh read of upstream docs — the REQUIRES table's overall shape (backrefs/lookaround/atomic-possessive/recursion/conditionals as the RE2-Rust-Vectorscan-TRE non-satisfying bloc, `pcre2-dfa`'s NFA-simulation automaton class, TRE's POSIX-longest bucket, Vectorscan's all-ends framing) is accurate and properly sourced. Where it breaks down is exactly where the brief predicted it might: tags that silently bundle two constructs with different evidence quality (S1), an unresolved ambiguity left to read as a clean "yes" by omission (S3), and — the more serious pattern across S1/S3/S4 — a fail-closed *declaration* policy (§5.3) that has no defense against a wrongly-satisfied capability, only against a wrongly-unsatisfied one; every semantics gap this review found is exactly that failure mode.

The measurement-validity side has one finding I'd call the most consequential in the file: **S6**. The cell-time arithmetic that sizes the whole first sample (~15-18 min/cell, ~1.7 h for six-to-seven testees, §3.5/§11.4) is validated on a homogeneous census and silently assumed to transfer to a set whose own headline family (redos-nested) is built to violate that homogeneity on the exact testees (`pcre2-interp`/`pcre2-jit`) the first sample runs. This isn't a hypothetical: the harness's `calibrate()` genuinely picks one `iters` from the median subject and applies it uniformly, so a catastrophic-backtracking witness's per-subject loop can run far longer than the model assumes. S7 (the set-wide `match`-regime exclusion generalizing a pcrec-specific bug) is the second-most consequential: it is a real, if perhaps unavoidable given the harness's sub-bench-scoped regime declaration, narrowing of what the whole roster can ever answer about compliance in this set's lifetime, and the design doesn't name that tradeoff or the alternative it's declining.

None of these findings overturns the design's core structure (the new sub-bench decision, Option B for `.rxt`, the fail-closed capability policy's shape, the outcome-enum adoption) — they are fixable within v0.1's own framework, mostly by tightening citations and adding the missing `hazard_class`/`automaton_class` assignments the design's own tables have slots for but leave blank.
