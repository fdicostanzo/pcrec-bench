## STEP 1 (static, ran) -- byte-diff the two pins' emitted C

**What was read**: both store records' `engine_metadata` for the
pattern (`store/records/capability@0.1/pcrec_{cf0962e3,25b1984f}_vm-in-
caps-simdna/*.jsonl`) -- `emit_bytes`/`emit_code_bytes`/`vm_program_bytes`
already read IDENTICAL (33,723 / 32,799 / 15,575) between the two
records, only `abi` differing (26 vs 27); `testee.build_flags` and
`environment.compiler_raw`/`.kernel`/`.cpu_model` also read identical
(gcc 15.2.0, same kernel, same CPU, same box, both windows) -- a first
static signal before any re-emission. `testees/pcrec/configs.toml`'s
`[testees.pcrec-vm-in]` (flags `--features all --engine=vm`) and
`testees/pcrec/adapter.py`'s real phase-1 argv construction (the
`EMIT_COMMENTS_FLAG` fixed protocol token, [B58]) were read to build the
exact re-emission command.

**What ran**: `docs/dev/measurements/probe_o38_movertime_emit_diff.py`,
re-emitting `wild-datetime-moment-iso8601` at both pinned binaries
already built on this box (`build/pcrec-cf0962e3`, `build/pcrec-
25b1984f` -- reused, no rebuild), under the vm-in config's real flags.
The pattern text was read from the store record itself and its sha256
checked against the record's own `canonical_sha256` before anything was
emitted. THE FLAG STORY, checked live rather than assumed: `-fcomments`
is a 25b1984f/abi-27 axis ([EMIT-VERB]/D112) that does **not exist** at
cf0962e3/abi 26 at all -- confirmed both by `--list-axes` (no `comments`
row) and by a live witness (cf0962e3 given `-fcomments` refuses by name:
"unknown option '-fcomments'"). cf0962e3 emitted full comments
UNCONDITIONALLY (there was nothing to toggle before [EMIT-VERB]
shipped), which is exactly what the adapter's `EMIT_COMMENTS_FLAG`
restores at 25b1984f -- so Comparison A (cf0962e3's only mode vs.
25b1984f WITH `-fcomments`) is the pair that matches what the two real
record-producing execs actually sent, not an apples-to-oranges guess.
Comparison B (25b1984f with vs. without `-fcomments`, at one pin) is
included for completeness, isolating the flag's own effect.

**Result**: Comparison A is **byte-identical modulo the abi stamp
line(s)** -- the ONLY two lines that differ anywhere in the `.c`/`.h`
pair are the provenance comment ("Generated by pcrec." -> "Generated by
pcrec (abi 27)." -- Note: this line also gains a parenthetical abi-27
which cf0962e3's earlier-abi shim never had reason to emit; the
prediction was "the abi stamp line", found here as TWO lines carrying
the abi digit) and the `.abi = 26` -> `.abi = 27` struct field. A
byte-for-byte diff (checked structurally, not by eyeballing -- the
script strips both known abi-bearing lines and requires the remainder to
match exactly, confirmed programmatically) proves this. Comparison B
(the `-fcomments` flag's own effect) differs exactly as expected --
comment prose only, `emit_size()`'s comment-excluded totals identical
across all three emissions (33,723 / 32,799 both pins, both flag
states).

**Verdict**: **STEP 1 EXONERATES THE EMITTED PROGRAM by construction.**
pcrec's I-79 (i) claim is confirmed directly on the one pattern that
moved, under the real build flags, on both real record-producing
compilers. The compiler/codegen side of the mover is closed; steps 2-3
are "the whole question" exactly as I-79 (ii) anticipated for this
outcome.

Archived: `docs/dev/measurements/2026-09-20-o38-movertime-emit-diff-
cf0962e3-vs-25b1984f.txt` (source header, verbatim output, D35 style);
script committed beside it, `--dry-run`-free and reproducible against

## A SECOND STATIC FINDING, not in the original three steps but load-bearing for how step 2 is read

Before treating STEP 2 ("cross the cf0962e3 artifact through the
25b1984f-era testee wrapper build and vice versa") as literally
runnable, I checked whether a "25b1984f-era wrapper build" actually
differs in source from the "cf0962e3-era" one. It does not:

- `git log --oneline -- testees/pcrec/shim.c testees/pcrec/driver.c`
  shows both files last changed at commit `7b49289` (2026-09-16, "[B42]
  restart step (4) HALF 2: fix KB-17"), **before** the cf0962e3 window
  even ran (2026-09-18). Neither file moved between the two windows that
  produced the two records O-38's mover compares.
- The one `testees/pcrec/adapter.py` change in that range, `7683b0e`
  ([B58], 2026-09-20), touches ONLY the phase-1 emit-c argv (adding
  `EMIT_COMMENTS_FLAG`) -- never phase 2 (the shim+artifact gcc build)
  or phase 3 (the driver invocation / buffer allocation). Its own commit
  message states this was verified inert on every quantity this project
  measures at the time it landed.
- Both store records' `environment.compiler_raw` read byte-identical:
  `gcc (Ubuntu 15.2.0-16ubuntu1) 15.2.0`, same kernel
  (`linux-7.0.0-29-generic`), same `cpu_model`. `testee.build_flags` and
  `testee.runtime_options` are also identical strings apart from the pin
  digit.

**Consequence**: there is no "wrapper era" to literally cross -- the
shim, the driver and the toolchain that built BOTH windows' `vm-in`
artifacts are the SAME files, the SAME gcc, on the SAME box. STEP 2's
literal brief cannot be executed as written; what remains informative,
and is what the prepared harness (below) runs once cleared, is: does
the ~x1.08 reproduce on a SAME-SESSION, same-wrapper, same-toolchain,
interleaved comparison of the two pins' artifacts, or was it an artifact
of the two historical windows being DAYS apart (2026-09-18 vs.
2026-09-20/21) with everything else about the box, the process, and the
allocator's own entropy free to differ between them regardless of any
source change? This reframes step 2 from "which build differs" (nothing
does) to "does the effect exist independent of calendar time", which is
the same axis STEP 3's buffer-placement instrument (posix_memalign
heap-address ASLR) is built to explain if it does.

  `build/b62witness-scratch/step23/driver_stepwitness.c`; the real
  `testees/pcrec/driver.c` (the file every pinned record's driver is

  (via `pcrecbench.driverrun.build_driver` against each pin's artifact,

**Why this matters even unrun**: `driver.c`'s `alloc_region()` allocates
both caller-provided regions via `posix_memalign` -- HEAP, once per
PROCESS -- so their addresses (and hence page/cache-line placement) are
expected to vary launch to launch under ASLR with **no source or
toolchain change at all**. Combined with the two static findings above
(the emitted program is exonerated; the wrapper source and toolchain are
provably unmoved between the two historical windows), this is the
leading remaining hypothesis, not yet confirmed -- steps 2 and 3 are
what would confirm or refute it, and neither has run.
