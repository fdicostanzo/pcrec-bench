# The two "22"s are ALMOST the same set, but not exactly: there is
# exactly ONE pattern on each side that the other does not have.
#
#   - `balanced-parens-rec` is in the POLICY's 22-unsup set (its sole
#     REQUIRES token, `recursion`, is withheld by rust-default's
#     declaration) but the RAW CENSUS shows it COMPILES. Confirmed live
#     below through the real `testees/rust/adapter.py` compile() path
#     (not just re-reading the archived census's COMPILED/REFUSED
#     line): the pattern is `\((?:[^()]|(?R))*\)`, and the mechanism is
#     a genuine rust-regex GRAMMAR FACT, not a fluke or a driver bug --
#     `(?R)` is not rejected syntax at all in this crate; `R` is one of
#     the crate's OWN real inline flag letters (CRLF mode), so `(?R)`
#     parses as an ordinary, valid, EMPTY flag-setting group (a
#     zero-width atom that can legally appear as one alternative inside
#     `(?:...)*`), and the pattern compiles clean. It does NOT implement
#     recursion: matched against the nested subject `(a(b)c)`, a real
#     recursive engine would match the WHOLE string [0,7); this driver's
#     compiled regex instead matches ONLY the inner pair, `(b)` at
#     [2,5) -- proof `(?R)` contributes nothing but a silent flag
#     toggle. The WITNESS pattern the capability census uses to test the
#     `recursion` token, `a(?R)?b`, happens to hit a DIFFERENT, genuinely
#     refused shape for an unrelated reason: `(?R)?` directly quantifies
#     the bare flag group with `?`, and a flag-only group is not a
#     quantifiable atom in this grammar ("repetition operator missing
#     expression") -- confirmed separately below: `(?R)` and `a(?R)`
#     alone both compile; `(?R)*` and `(?R)?` both refuse with the same
#     message, REGARDLESS of whether `(?R)` would otherwise do anything
#     useful. `balanced-parens-rec`'s own quantifier is applied to the
#     ENCLOSING `(?:...)*` group, never to `(?R)` directly, so it avoids
#     the one shape the isolated witness happens to hit. Net: this is
#     the corpus-level instance of the "syntax accepted but semantics
#     wrong" class the task brief's `possessive-quantifier` precedent
#     names -- a REAL corpus disagreement between "the token-level
#     witness pattern refuses" and "the corpus pattern that motivated
#     the token compiles to something silently unrelated to what its
#     REQUIRES tag claims it needs" -- not a bug in the policy, the
#     census, or the adapter; each is behaving exactly as designed on
#     its own one-witness-per-token model, which cannot see a second
#     spelling of the same construct behaving differently.
#
#   - `mojibake-curly-quote` is in the CENSUS's 22-refused set but NOT
#     in the policy's 22-unsup set, because its sole REQUIRES token
#     (`non-utf8-subject`) IS satisfied by rust-default's declaration --
#     it reaches the driver in BOTH the policy path and the raw census,
#     and refuses in both, for the SEPARATE, already-fully-documented
#     I-72 pattern-source-UTF-8 reason (`testees/rust/CLAUDE.md`'s own
#     "mojibake-curly-quote refuses ... the driver's own pre-regex-crate
#     UTF-8 validation" section): a lone raw byte 0x93/0x94 in the
#     PATTERN TEXT itself is not valid UTF-8, and `regex::bytes::
#     RegexBuilder::new` takes `&str` for the pattern source (never
#     `&[u8]`, unlike the haystack). This is the report's own "refused"
#     row (matrix.tsv), not a second unsup row -- so it is not actually
#     a set MISMATCH in the sense of an unexplained finding; it is the
#     matrix correctly keeping this one pattern OUT of "unsup" (because
#     its token is satisfied) while the raw census correctly marks it
#     refused (because it fails for a real, different, off-vocabulary
#     reason). No new finding here beyond confirming the accounting
#     closes with zero unexplained patterns.
#
