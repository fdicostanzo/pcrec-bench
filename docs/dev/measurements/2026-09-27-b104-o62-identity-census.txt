# ============================================================
#
# Q: does program_identity's v2 normalization exclude the emitted STAMP
#    lines (RX_REQ_BYTE/_RUN/_WHY, RX_END_WINDOW, RX_VM_START, RX_TUNE...)?
#    If those count, "changed" is inflated by stamp text and does not mean
#    the program changed.
#
# A: YES, it excludes them -- CONFIRMED EMPIRICALLY on real emitted text,
#    not merely read from the module's own docstring (tools/program_
#    identity.py's rule 3: "every #define NAME line whose NAME is #define'd
#    on ONE side only"). Check 1 above shows 25b1984f (abi 27) emits NONE
#    of RX_REQ_BYTE/_RUN/_WHY/RX_END_WINDOW at all -- the feature does not
#    exist in that build -- while 751b9c6d (abi 39) emits all four; after
#    normalize_one, NEITHER side's normalized text contains any of those
#    five stamp names. RX_TUNE is NOT in this category (it predates
#    25b1984f, landing at abi 26/cf0962e3), so it is compared VERBATIM on
#    both sides per rule 3's own scope -- but its value is a fixed tuning
#    constant this project's own configs do not vary, so it contributes no
#    movement either.
#
#    Check 2 diffs THREE independent "changed" rows, one per set (email,
#    syntax, bounded), and every single one is a REAL, FUNCTIONAL code
#    difference -- never a stamp remnant:
#      - email/factored (auto-caps, plain): a memchr NECESSARY-BYTE GUARD
#        (byte 64 = '@', the pattern's own required byte) -- [OPT-REQBYTE]'s
#        own emitted code, exactly as CLAUDE.md's abi-29 entry describes
#        ("a memchr guard + #include").
#      - syntax/alt-nested (whole-subject): a SEARCH_FROM CLAMP to the last
#        3 bytes (the pattern's own minimum match length) -- [OPT-ENDWIN]'s
#        own emitted code ("a search_from clamp").
#      - bounded/cls-lazy-16384 (whole-subject): the SAME search_from clamp
#        mechanism, at 16384 bytes (this pattern's own minimum length).
#    All three diffs are 1-2 new lines of REAL C, inserted at the top of
#    rx_search's body, nothing else moved -- and in every case the ONLY
#    lines differing are these, never a stamp #define (confirmed: none of
#    the three diffs contains a `#define` line at all).
#
# CONCLUSION: the predictor is NOT weak on this account. "changed" in the
# 1,110-row census means a real, functional program difference every time
# it was checked (3/3 witnesses, one per set, chosen before this check
# ran -- not cherry-picked after the fact: email/factored was the FIRST
# "changed" row in the census file by construction; syntax/alt-nested and
# bounded/cls-lazy-16384 were chosen only for being different SETS, not for
# their diff content, which was read only afterward). This does not prove
# EVERY one of the 692 "changed" rows is a real code difference -- three
# witnesses are a spot check, not an exhaustive proof -- but it does rule
# out the specific failure mode asked about (stamp-line-only inflation),
# and it is consistent with what landed in the abi 29-37 pin range
# ([OPT-ANCHOR-VM]/[OPT-ENDWIN]/[OPT-REQBYTE] at abi 29, [OPT-FREQPICK]/
# [OPT-REQPOS] at abi 30, [OPT-PRECHECK-ADMIT] at abi 31, K64 at abi 33,
# K65/K66/[OPT-LITSCAN] S1 at abi 35-37 -- CLAUDE.md's own history) being
# real optimization work that touches emitted code, not merely new
