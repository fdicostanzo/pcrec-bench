# THE MECHANISM (established by the PCRE2_NO_UTF_CHECK ablation below, on
# all three routes, and by comparing pcre2_jit_match() called DIRECTLY
# against pcre2_match() called on a JIT-compiled pattern -- the shape
# testees/pcre2/driver.c's `do_match` actually uses for the pcre2-jit
# testee, per its own header comment: "never calls a separate
# pcre2_jit_match: pcre2_match() itself dispatches to JIT-compiled code
# internally when present").
#
# libpcre2 10.46's pcre2_match() and pcre2_dfa_match() both validate the
# WHOLE subject as well-formed UTF-8 before their own scan begins, unless
# the caller passes PCRE2_NO_UTF_CHECK (man pcre2api, quoted already in
# testees/pcre2/driver.c's header and in this project's own [B94]/BD15
# VALIDATE-ONCE fix). That validation cost is NOT flat per byte across
# scripts: on this box, validating 65536 bytes of `t-64k-cyr` (88.3%
# multi-byte, 36555 characters, dominant lead byte 0xd0 -- Cyrillic is a
# 2-byte-per-character UTF-8 script) costs ~3.04-3.13x what validating
# the SAME BYTE COUNT of `t-64k-asc` (100% single-byte ASCII, 65536
# characters) costs, on EVERY route that reaches it:
#
#   - pcre2_match() on an interp-only compile (`pcre2-interp`'s own call
#     shape)                                             ratio ~3.04-3.06
#   - pcre2_dfa_match()  (`pcre2-dfa`'s own call shape)   ratio ~3.12-3.13
#     (one outer-run outlier at 3.44, flagged above, not excluded)
#   - pcre2_match() on a JIT-compiled pattern (`pcre2-jit`'s ACTUAL call
#     shape, per driver.c's own documented internal-dispatch design)
#                                                          ratio ~3.05-3.06
#
# Forcing PCRE2_NO_UTF_CHECK on every one of these three call shapes
# COLLAPSES the ratio to ~1.00 on both scripts (interp_nocheck,
# dfa_nocheck, jit_via_match_nocheck below) AND brings the absolute cost
# down to the SAME level as byte-mode (no PCRE2_UTF at all) on the same
# subjects -- the entire ~3x-more-expensive-on-Cyrillic cost IS the
# validation pass, on all three routes, full stop.
#
# The LOWER-LEVEL pcre2_jit_match() entry point -- which the real bench
# testee NEVER calls, per driver.c's own header comment -- shows NO
# script penalty at all, check or no-check (jit_direct_check/nocheck
# below, flat ~0.038 ns/B on BOTH scripts in every run). This localises
# the cost precisely: it lives in pcre2_match()'s/pcre2_dfa_match()'s own
# pre-dispatch validation call, which pcre2_jit_match() bypasses (or
# performs far more cheaply as part of its own vectorized matching code) --
# and it is EXACTLY the call shape `do_match` in testees/pcre2/driver.c
# uses for all three real testees (pcre2-interp/-dfa/-jit alike, since
# pcre2-jit never calls pcre2_jit_match either). So the ~3.05-3.12x found
# in the committed report is a REAL, UPSTREAM libpcre2 characteristic --
# not a driver/harness artifact, not specific to this project's find-all
# loop (this probe uses a single, isolated match call per measurement, no
# loop at all, because `floor` never matches -- there IS only one call in
# the real find-all path either, per bench/utf8/expectations.tsv).
#
# CONTROL (the find-all loop on ' ', a common byte that DOES match often,
# replicating driver.c's own VALIDATE-ONCE call shape: call 1 unchecked,
# calls 2..n forced PCRE2_NO_UTF_CHECK): the ratio here runs the OPPOSITE
# direction and is much smaller (~1.12-1.20, asc COSTLIER than cyr) --
# consistent with the mechanism above: once the ONE-TIME validation cost
# is amortised across many per-match calls (9216 on asc vs 7214 on cyr,
# `t-64k-cyr`'s fewer, longer-encoded words giving fewer space-separated
# matches per fixed byte budget), the per-match loop overhead dominates
# and the validation asymmetry is swamped. This is the NEGATIVE control
# that isolates `floor`'s own ONE-CALL, ZERO-MATCH shape as the reason
# the ratio is visible there and not on every pattern in the set.
#
