# CB6 -- k-reset (\K), resolved by WITNESS (N2's own hedge: "not general
# PCRE-style \K; has its own reset-point extensions under some syntaxes"
# -- neither a clean yes nor no)
# =====================================================================
#
# VERDICT: SATISFIED, AND ARCHITECTURALLY EQUIVALENT TO PCRE's \K, under
# ONIG_SYNTAX_PERL_NG (and OnigSyntaxPerl, OnigSyntaxPython,
# OnigSyntaxOniguruma, OnigSyntaxRuby -- every shipped syntax but the
# POSIX-family ones, Emacs/Grep/GnuRegex/Java/ASIS):
#
#   oniguruma.h:508  ONIG_SYN_OP2_ESC_CAPITAL_K_KEEP (1U<<22) -- "\K"
#   regparse.c:5773-5775  `case 'K': if (!IS_SYNTAX_OP2(syn,
#     ONIG_SYN_OP2_ESC_CAPITAL_K_KEEP)) break; tok->type = TK_KEEP;`
#   regparse.c:2809  `node_new_save_gimmick(node, SAVE_KEEP, env)`
#
#   THE MECHANISM (regexec.c, the runtime): `\K` compiles to a
#   SAVE_VAL/SAVE_KEEP gimmick. At match time (regexec.c:4319-4340,
#   CASE_OP(SAVE_VAL)/case SAVE_KEEP): `STACK_PUSH_SAVE_VAL(mem, type,
#   s)` -- the CURRENT position `s` is pushed onto oniguruma's own
#   BACKTRACKABLE stack (so a `\K` inside a branch that later backtracks
#   is correctly undone, exactly as PCRE's \K is). At
#   UPDATE_VAR_KEEP_FROM_STACK_LAST (regexec.c:4350-4351):
#   `STACK_GET_SAVE_VAL_TYPE_LAST(SAVE_KEEP, keep)` pops the saved
#   position back into the local `keep` variable. On overall match
#   success (regexec.c:3070 initializes `keep = s = sstart`; ~3121
#   `if (keep > s) keep = s;`; ~3127/3141 `region->beg[0] = keep - str`
#   / `rmt[0].rm_so = keep - str`): `keep` OVERRIDES the REPORTED match
#   START, without moving the actual search anchor point (backtracking,
#   any lookaround before the `\K`, all work exactly as without it).
#   This is PCRE's \K semantics precisely, not an approximation.
#
#   Live confirmation: `a\Kb` COMPILES (pass 1 below); `bench/email`'s
#   own quick run (this lane, `quick --regime match --testee
#   onig-default`) independently confirms the whole-subject `\z`-wrapped
#   artifact answers 5/5 as expected on real corpus subjects, which
#   would not hold if `\K`/anchor interaction were subtly wrong on any
#   witnessed pattern using it.
#

#
# 1. lookaround vs lookbehind-variable -- CB5-style split confirmed on
#    REAL corpus text, not just the isolated witness: 9 of 10
#    `requires-lookaround` patterns compile clean; the ONE failure
#    (`negation-scope-lookbehind-var`) ALSO carries `requires-
#    lookbehind-variable`, and the isolated witness `(?<=a|bc)x`
#    (branches of differing fixed width) reproduces the SAME refusal
#    (-122, "invalid pattern in look-behind") in isolation. Fixed-width
#    lookbehind and lookahead are both fine; a lookbehind whose
#    ALTERNATIVES differ in width is not -- exactly the tag's own
#    definition ("a lookbehind whose body is not fixed-width").
#    DECLARED: `lookaround` satisfied, `lookbehind-variable` not.
#
# 2. recursion -- SATISFIED, but with a documented SPELLING gap, not a
#    capability gap: `(?1)`, `(?&name)`, `(?0)`, `\g<1>` and `\g<name>`
#    all compile (five independent, functioning recursion/subexp-call
#    spellings); PCRE's `(?R)` shorthand for "recurse into the whole
#    pattern" specifically does NOT parse under Oniguruma (-116,
#    "unmatched close parenthesis" -- `R` is not a recognised group-
#    option character at all, so the parser reads the rest of the
#    pattern as ordinary text and the closing `)` count goes wrong).
#    CONFIRMED on real corpus text: `nested-comment-rec` (`(?1)`) and
#    `bracket-array-define` (`(?(DEFINE)...)` + `(?&brackets)`) both
#    compile; `balanced-parens-rec` (`(?R)`) is the ONE corpus refusal
#    in this family, reproducing the isolated witness exactly.
#    `(?0)` (Oniguruma's own "call group 0 = the whole pattern"
#    convention) is confirmed live as `(?R)`'s functional replacement --
#    a `variant.kind: syntax-only` rewrite for a future set that wants
#    to run this pattern on `onig-default` (capability_set_v1.md 6.2's
#    rewrite-table shape; not built by this lane, which does not touch
#    bench/capability's own variant declarations).
#    DECLARED: `recursion` satisfied. `balanced-parens-rec` is left to
#    fail HONESTLY as a real, per-pattern `did-not-compile`
#    (`refusal_class: syntax`, this adapter's own derivation) rather
#    than being hidden behind a wholesale `unsupported-by-declaration`
#    that would misreport 2 of 3 real recursion patterns as untestable.
#
# 3. control-verbs -- NOT SATISFIED, despite a coincidence worth
#    recording rather than glossing over: `(*FAIL)` and `(*SKIP)`
#    COMPILE. This is NOT partial control-verb support -- Oniguruma has
#    its own, structurally different CALLOUT mechanism
#    (ONIG_SYN_OP2_ASTERISK_CALLOUT_NAME, present under Perl_NG) with a
#    small BUILT-IN callout registry (src/ascii.c's own `init()`:
#    `name = "FAIL"; BC0_P(name, fail); name = "MISMATCH"; ...`) that
#    happens to share PCRE's `(*NAME)` SYNTAX for two of PCRE's five
#    control-verb names. `(*ACCEPT)` is not in that registry ("undefined
#    callout name", -229) -- the corpus witness this lane's real corpus
#    would need is absent; this lane did NOT verify that a compiling
#    `(*FAIL)`/`(*SKIP)` callout produces PCRE's exact backtracking
#    behaviour (a callout can invoke a user-supplied function; onig's
#    OWN default when none is registered is unverified against PCRE's
#    control-verb semantics byte for byte). Per the SAME precedent
#    testees/pcre2/CLAUDE.md's own "pcre2-dfa" section sets ("every
#    backtracking control verb except `(*FAIL)`... this vocabulary has
#    no finer token for 'FAIL only'"), the token is withheld WHOLESALE
#    rather than half-claimed.
#
# 4. unicode-properties -- NOT SATISFIED under this lane's ENCODING
#    CHOICE (ONIG_ENCODING_ASCII, testees/onig/CLAUDE.md deliverable
#    (d)), and this is the census's own "wrong first-cut" catch: a
#    first-cut declaration reading only "does `\p{...}` PARSE" would
#    have said yes (the OP2 flag is present under Perl_NG, and
#    `\p{Alpha}` genuinely compiles). But `\p{L}` -- a REAL Unicode
#    General Category name, the shape every PCRE `\p{...}` corpus
#    pattern actually uses -- is REFUSED ("invalid character property
#    name {L}", -223). Under ASCII encoding, Oniguruma's property table
#    is POSIX-style ctype names only (`Alpha`, `Digit`, `Space`, ...),
#    NOT Unicode General Categories/Scripts -- a narrower, DIFFERENT
#    vocabulary than PCRE's, not a subset of it by coincidence of
#    spelling. bench/capability@0.1 happens to tag ZERO patterns
#    `requires-unicode-properties` today (the corpus census above), so
#    this finding changes no CURRENT ranking -- it is recorded here so
#    a FUTURE set (or a future onig config compiled under
#    ONIG_ENCODING_UTF8, where real \p{...} property tables load) is
#    not silently mis-declared by copying this row forward unread.
#    DECLARED: `unicode-properties` NOT satisfied for `onig-default`.
#
# 5. named-groups -- SATISFIED: `(?<name>...)` (Oniguruma's/Ruby's own
#    spelling, also PCRE's) compiles; `(?P<name>...)` (Python's
#    spelling) does not (-119, "undefined group option" -- ESC's `P` is
#    not recognised as a named-group introducer under Perl_NG at all).
#    The tag's own definition is "any named-group spelling", and
#    `wild-logparse-syslogbase-expanded` (the corpus's one `requires-
