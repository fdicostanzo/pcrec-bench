  give-up REACHABLE for testees/tre/driver.c, i.e. can tre_regnexecb()'s

  timing claim rests on wall-clock, only on a fixed 8 s per-cell budget
  used to bound total run time; loadavg before 0.51/0.38/0.42, ordinary
  background load, does not affect an allocation count).
Script: probe_kb29_tre_giveup_reachability.py (this directory), which
  builds and runs probe_kb29_tre_giveup_reachability.c (the driver.c-
  shaped two-call find-all probe) under probe_kb29_tre_failmalloc.c (an
  LD_PRELOAD malloc/calloc/realloc call counter, TRE_FAILMALLOC_VERBOSE=1,
  no failure injected -- TRE_FAILMALLOC_AT unset). Command:
  `python3 probe_kb29_tre_giveup_reachability.py` from this directory.
Method, precisely: testees/tre/driver.c's find-all loop calls
  tre_regnexecb() repeatedly, advancing `pos` by KB-17's rule. This probe
  reproduces exactly that shape as two calls: call 1 (pos 0) is given
  only the subject's leading byte, so it matches a literal alternative
  trivially and cheaply; call 2 (pos 1) receives the REST of the subject
  and the pattern's OWN backreference groups, which is what routes TRE to
  its backtracking matcher at all (has_backrefs, testees/tre/CLAUDE.md's
  own `automaton_class` section) -- exactly the population a real
  KB-29 mid-loop witness needs (find-all call 1 already succeeded; call 2
  is where a give-up would have to originate). The subject is
  "Xa" + N x 'b' with NO trailing 'c', so the pattern
  X|a(b*)(b*)...\1\2...c can never find its required 'c' and call 2 must
  fully explore the backtracking search space before answering NOMATCH --
  the worst case for the search to need memory, if it ever does. The
  LD_PRELOAD interposer counts every malloc/calloc/realloc call the WHOLE
  process makes; three stderr MARK lines around compile()/call1/call2
  let the script attribute each allocation to its phase. A cell that
  would run past 8 seconds of wall time (pure CPU, not an allocation
  question -- TRE's backtracking search is exponential in TIME for these
  patterns) is killed and excluded from the total, named explicitly
  rather than silently treated as "0 allocations".
Prior context this probe follows up on: testees/tre/CLAUDE.md's own
  "gave-up: PROVISIONED by design, UNWITNESSED on this corpus" section
  already tried ONE 5-way backreference pattern over 40 bytes under a 2 s
  alarm and did not reproduce TRE_MAX_STACK's REG_ESPACE (REG_NOMATCH
  came back inside the alarm). This probe widens that check to 1/3/5/7
  backreference groups and b-run lengths from 10 B to 1,000,000 B (at 1
  group; fewer at higher group counts, capped by the 8 s budget), and
  asks a SHARPER, mechanism-level question directly: does the exec call
  ever ALLOCATE at all? (Not: does a specific pattern/subject/timeout
  combination happen to reproduce REG_ESPACE.)

READING (mine, not the script's -- the file's own convention keeps
interpretation out of the printed block above)
======================================================================
Zero allocations were observed inside ANY tre_regnexecb() exec call in
this build, across every combination this probe could complete (1-7
backreference groups, subjects from 10 B to 1,000,000 B). Cross-checked
against libtre's own source (lib/tre-mem.c, lib/tre-stack.c, fetched
2026-09-26): REG_ESPACE -- the ONLY code besides REG_OK/REG_NOMATCH TRE's
regexec-family functions can return -- is returned exclusively when a
real malloc()/calloc()/realloc() call fails, or when tre_stack_push()'s
own internal doubling would exceed its max_size cap (itself reached only
through further allocation). Since no allocation of any kind happens
inside an exec call here, REG_ESPACE (or any other non-OK/non-NOMATCH
code) CANNOT arise from testees/tre/driver.c's find-all loop's SECOND (or
later) tre_regnexecb() call on this pinned libtre build -- the KB-29 bug
shape this lane fixed defensively in driver.c (mirroring pcre2/onig/
pcrec) is therefore UNREACHABLE here, not merely hard to hit by chance.
The only place REG_ESPACE CAN fire is tre_regncompb() (compile time),
which testees/tre/CLAUDE.md's `refusal_class` section already handles as
a first-class `did-not-compile` (size-limit when the pattern's own byte
length exceeds TRE_MAX_RE, absent otherwise -- TRE overloads REG_ESPACE
between the two causes and this project already declines to guess which).
This does NOT rule out some future libtre build (a different version, a
different allocator, a different build configuration) behaving
differently -- the fix in driver.c stays in place as a defensive, no-cost
correctness improvement for that hypothetical, mirroring the three
already-fixed drivers exactly.
